Seeds — loading raw CSVs into the warehouse

Your warehouse is connected and empty. To build models, you need something to model from. In a real project the “something” is data piped in by Fivetran, Airbyte, or a custom ingestion job. For learning, we use dbt’s built-in mechanism for loading static CSVs — seeds.

What is a seed?

A seed is a CSV file under seeds/ in your dbt project. When you run dbt seed, dbt:

  1. Reads each CSV.
  2. Infers column types (or uses ones you declare).
  3. Issues a CREATE TABLE in the warehouse named after the file (e.g. raw_customers.csv → table raw_customers).
  4. INSERTs every row.

From dbt’s perspective seeds behave just like any other model: they have a name, they live in the manifest, you can {{ ref('raw_customers') }} them from a model.

When to use seeds — and when not to

Good fit Bad fit
Lookup tables (country codes, ISO currency, plan tier → price) Operational data (orders, events, users)
Sample / fixture data while learning or building demos Anything that updates more than once a quarter
Small reference tables that change with code, not with the business Anything bigger than a few thousand rows

The rule of thumb: if it would feel weird to git diff the data, it doesn’t belong in a seed. Production data flows in through ingestion, not through commits.

The jaffle_shop sample data

This course ships with three CSVs in data/ (top-level, outside dbt_project/):

File Rows What it represents
raw_customers.csv ~100 Customer records: id, first_name, last_name
raw_orders.csv ~99 Orders: id, user_id, order_date, status
raw_payments.csv ~113 Payment events: id, order_id, payment_method, amount

This is the canonical jaffle_shop dataset that ships with dbt’s own tutorials. It pretends to be a small e-commerce shop selling Australian breakfast sandwiches. Tiny on purpose — you can hold the whole schema in your head while learning.

Why are the CSVs in data/ instead of dbt_project/seeds/? Because dbt_project/ is gitignored — if we put the CSVs there, dbt-learn reset would delete them. Keeping them in data/ means a reset only nukes your work, not the source data.

After this completes, database/dev.duckdb contains three real, queryable tables. You can verify by opening the file with the DuckDB CLI:

duckdb database/dev.duckdb -c "SELECT count(*) FROM raw_customers;"

Common pitfalls

  • Putting CSVs in the wrong directory. — They have to live under dbt_project/seeds/. dbt seed won’t look at data/, the project root, or anywhere else.
  • Treating seeds like a load mechanism. — Seeds are slow for big files because every row goes through SQL INSERT statements. Real ingestion uses bulk-load APIs (COPY, LOAD DATA, or vendor-specific connectors). For anything > a few MB use a real loader.
  • Hardcoding seed table names downstream. — Always reference seeds via {{ ref('raw_customers') }}, never SELECT * FROM main.raw_customers. ref() works in dev, ci, prod — hardcoded names break the moment the schema changes.
