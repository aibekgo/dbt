Configuring dbt_project.yml

You’ve been editing models, declaring sources, and running dbt run — but the file that actually defines your project is dbt_project.yml. Every dbt run reads it first to figure out where models live, which warehouse to talk to, and what defaults to apply. Time to actually look at it.

What is dbt_project.yml?

Every dbt project has exactly one dbt_project.yml at its root. It’s the project’s config file — a single YAML file that tells dbt:

  • What this project is called.
  • Which connection profile from profiles.yml to use.
  • Where to find models, seeds, tests, macros, snapshots.
  • What defaults (materialization, schema, tags, etc.) to apply to which folders.

Without dbt_project.yml, dbt has nothing to anchor to — dbt run from a directory without it just errors out. Whenever you change project-wide behavior, this is the file you edit.

Walking through the file

Here’s the full file dbt init generated for you, broken down section by section:

1. Identity

name: 'dbt_project'
version: '1.0.0'

The project’s name and version. The name matters — it shows up later as the top key under models:, and it’s how dbt qualifies your models in compiled SQL. version is just metadata.

2. Profile

profile: 'dbt_project'

Which entry in profiles.yml dbt should use. Remember: profiles.yml can contain many profiles (dev, prod, snowflake_prod, …). This line picks one.

3. Path configs

model-paths:    ["models"]
analysis-paths: ["analyses"]
test-paths:     ["tests"]
seed-paths:     ["seeds"]
macro-paths:    ["macros"]
snapshot-paths: ["snapshots"]

Where dbt looks for each kind of resource. The defaults match the folder names dbt init created — you almost never change these. They’re here so you could, e.g. point seed-paths at data/ instead.

4. clean-targets

clean-targets:
  - "target"
  - "dbt_packages"

What dbt clean deletes. target/ is dbt’s build output (compiled SQL, manifest, run results); dbt_packages/ is where dbt deps installs third-party packages. Running dbt clean wipes both.

5. The models: block — the configuration workhorse

models:
  dbt_project:                # ← matches `name:` at the top
    example:
      +materialized: view

This is where you set folder-level defaults. The structure reads top-down:

  • models: — “here come configs that apply to models.”
  • dbt_project: — the project name. Has to match name: above. (Lets one dbt_project.yml configure multiple installed packages.)
  • example: — a folder under models/. Anything in models/example/*.sql picks up the configs nested below.
  • +materialized: view — the actual config. The leading + tells dbt “this is a config, not a sub-folder name.” Without it, dbt would look for models/example/materialized/view.sql and silently ignore your intent.

You’ll edit this block in the exercise to set per-folder materialization defaults.

Materialization, briefly

A materialization is what dbt does with the SQL you wrote — the kind of object it creates in the warehouse. Same SELECT, different storage strategy.

Materialization What dbt issues Best for
view (default) CREATE OR REPLACE VIEW Cheap to build. Reads recompute every time. Staging models, light transforms.
table CREATE OR REPLACE TABLE Expensive to build, fast to read. Marts, anything queried by dashboards.
incremental INSERT / MERGE for new rows Big append-only tables (events, logs). Builds only new rows on each run.
ephemeral Inlined as a CTE in downstream models Reusable SQL fragments. Never lands in the warehouse.

You don’t need to remember the syntactic details of incremental or ephemeral right now — just know they exist. The two you’ll use 95% of the time are view for staging (cheap, recompute-on-read) and table for marts (paid once, fast forever).

Folder-level config in practice

The whole reason dbt_project.yml has a models: block is so a 200-model project can say “everything in staging/ is a view, everything in marts/ is a table” in five lines — instead of pasting {{ config(materialized='...') }} at the top of every file.

models:
  dbt_project:
    staging:
      +materialized: view
    marts:
      +materialized: table

That’s the convention you’ll set up in the exercise. To prove it works, you’ll add a second model — dim_customers — under models/marts/, and watch dbt build it as a table instead of a view, with no config() block in the SQL file.

Three places to set materialization

For completeness — dbt resolves materialization in increasing specificity. Most specific wins.

  1. Project-wide in dbt_project.yml: models: { +materialized: view } — everything, unless overridden.
  2. Folder-level in dbt_project.yml: staging: { +materialized: view } — this is the workhorse.
  3. Per-model in the SQL file: {{ config(materialized='incremental') }} — the escape hatch for one-off cases.

What you’ll do in the exercise

Three small steps to see folder-level config in action:

  1. Create a new model at models/marts/dim_customers.sql. Plain SELECT from {{ ref('stg__customers') }} — no {{ config() }} block at the top.
  2. Edit dbt_project.yml — replace the existing models: block with one that sets +materialized: view for the staging/ folder and +materialized: table for the marts/ folder.
  3. Run dbt run and watch the log: stg__customers builds as a view, dim_customers builds as a table — even though neither SQL file has a config() block. The materialization came entirely from the folder config.

Common pitfalls

  • Forgetting the + sigil. — Without it, dbt treats materialized: view as a folder path. Confusing parse errors or silent no-op.
  • Wrong project name. — The second key under models: must match name: at the top of the same file. If they disagree, dbt silently ignores your config.
  • Indentation drift. — YAML uses spaces, two per level. Mixing tabs or 3-space indents breaks things in non-obvious ways.
  • Setting it per-model when you could set it per-folder. — Works, but means every new model needs the boilerplate. Folder-level config wins for any project bigger than a handful of models.

Exercise walkthrough

Steps

1. Make sure you’re inside dbt_project/:

cd dbt_project   # if you're not already here

2. Create the marts folder and a new model called dim_customers:

mkdir -p models/marts
touch models/marts/dim_customers.sql

3. Paste this into models/marts/dim_customers.sql:

select
    customer_id,
    first_name,
    last_name
from {{ ref('stg__customers') }}

Two things to notice:

  • No {{ config(materialized='table') }} at the top. The materialization will come entirely from dbt_project.yml in the next step.
  • {{ ref('stg__customers') }} — marts depend on staging models via ref(), the same way staging depends on raw via source(). dbt will build stg__customers first, then dim_customers.

4. Open dbt_project/dbt_project.yml. Scroll to the bottom — dbt init left you a models: block that points at the demo example/ folder:

models:
  dbt_project:
    example:
      +materialized: view

Replace it with two folder configs — one for the staging/ folder, one for the new marts/ folder. The key change is +materialized: table on the marts block — that’s what flips dim_customers from a view (the default) to a table.

models:
  dbt_project:
    staging:
      +materialized: view
    marts:
      +materialized: table

What this YAML says:

  • models: — top-level config block
  • dbt_project: — your project name (must match the name: field at the top of the same file)
  • staging: and marts: — folders under models/ that the configs apply to
  • +materialized: <view|table> — the leading + marks the line as a config, not a sub-folder. Without +, dbt looks for a folder called materialized/ containing view.sql and silently no-ops.

5. Build everything:

dbt run

You should see two green nodes — stg__customers (view) and dim_customers (table). Look closely at the log:

1 of 2 OK created sql view  model main.stg__customers ...
2 of 2 OK created sql table model main.dim_customers ...

The words view and table come from the folder-level config you just set.

6. Sanity check the materializations actually differ in the warehouse:

duckdb ../database/dev.duckdb -c "
  select table_name, table_type
  from information_schema.tables
  where table_schema = 'main_main'
  order by table_name;
"

Expected:

┌────────────────┬────────────┐
│   table_name   │ table_type │
├────────────────┼────────────┤
│ dim_customers  │ BASE TABLE │
│ stg__customers │ VIEW       │
└────────────────┴────────────┘

7. Press v.

What the verifier checks

  • dbt run --select +dim_customers exits 0 (the + prefix means “this and all upstream”).
  • target/manifest.json reports dim_customers resolved to materialized: table.
  • target/manifest.json reports stg__customers is still materialized: view.

If both materializations come out right, your folder-level config is wired correctly.

Common failure modes

Symptom Fix
Compilation Error: Model 'dim_customers' depends on a node named 'stg__customers' which was not found The staging model wasn’t built yet. Run dbt run (no select) — +dim_customers covers it but full dbt run is foolproof.
dim_customers shows up as VIEW in DuckDB Either your marts: block is missing the + on materialized, or it’s nested under the wrong project name. Re-check the YAML against step 4.
YAML parse error / Could not run dbt Indentation. Two spaces per level, no tabs.
