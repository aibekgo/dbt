Configuring dbt_project.yml

Your stg_customers model is built as a view — that’s dbt’s default. In a real project you’ll want different layers built differently: staging as views, marts as tables, snapshots as their own thing. dbt_project.yml is where you declare those defaults.

What is a materialization?

A materialization is what dbt does with the SQL you write — the kind of object it creates in the warehouse:

MaterializationWhat dbt issuesBest for
view (default) CREATE OR REPLACE VIEW Cheap to build. Reads recompute every time. Fine for staging and small lookups.
table CREATE OR REPLACE TABLE Expensive to build, fast to read. Use for marts and anything queried by dashboards.
incremental INSERT / MERGE for new rows Big append-only tables (events, logs). Builds only the new rows on each run.
ephemeral Inlined as a CTE in downstream models Reusable SQL fragments. Never lands in the warehouse.

Same SQL, different storage strategy. Switching a model from view to table changes nothing about the query — only about how dbt stores the result.

Three places to set materialization

dbt resolves materialization in increasing specificity. The most specific wins.

  1. Project-wide default in dbt_project.yml 
    models:
  +materialized: view   # everything in the project, unless overridden
  2. Folder-level default in dbt_project.yml — the workhorse. 
    models:
  dbt_project:
    staging:
      +materialized: view
    marts:
      +materialized: table
  3. Per-model in the SQL file — the escape hatch. 
    -- models/marts/orders_summary.sql
{{ config(materialized='incremental', unique_key='order_id') }}

select ...

In a real project, 95% of materializations come from the folder-level config. The per-model config() block is for the special cases — the one model that needs to be incremental, the one staging model you want as a table for some performance reason.

The leading + sigil

Notice +materialized, not materialized. The + tells dbt “this is a configuration to apply to every model in this folder” instead of “this is the name of a sub-folder.”

models:
  dbt_project:
    staging:
      materialized: view   # ← WRONG: dbt looks for models/staging/materialized/view.sql
      +materialized: view  # ← RIGHT: applies to every model under staging/

You’ll see the same pattern with +enabled, +tags, +schema, +meta, and any other config dbt understands.

Why set it explicitly when view is already the default?

Two reasons:

  • Future-proofing. When you decide later that staging should be ephemeral or table for some reason, you change one line in dbt_project.yml instead of editing every staging model.
  • Documentation. A reader of your repo sees the materialization choice declared in one place. No surprise behavior depending on which dbt version’s defaults are in play.

What the verifier checks

The verifier runs dbt parse to refresh target/manifest.json, then inspects the manifest entry for stg_customers and confirms its config.materialized resolved to view. The manifest is dbt’s own ground-truth view of what each model is configured as — if it reads view there, dbt agrees with you.

Common pitfalls

  • Forgetting the + sigil. — Without it, dbt treats materialized: view as a path. Confusing parse errors.
  • Wrong project name. — The second key under models: must match name: at the top of the same file. If they disagree, dbt silently ignores your config.
  • Indentation drift. — YAML uses spaces, two-per-level. Mixing tabs or 3-space indents breaks the file in non-obvious ways.
  • Setting it per-model when you could set it per-folder. — Works, but means every new model needs the boilerplate. Folder-level config wins for any project bigger than a handful of models.
