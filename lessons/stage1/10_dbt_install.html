Stage 1 — Your First dbt Project

Stage 0 was concept-only. From here on, you write real code against a real warehouse. By the end of this stage you’ll have a working dbt project with raw seed data loaded into DuckDB and your first model materialized as a table.

You build it. The repo doesn’t ship a pre-made dbt_project/ — you create it yourself with dbt init, write the profiles.yml, drop in the seed CSVs, and run the first model. That way nothing is magic.

What you already have installed

When you ran uv pip install -e . during setup, you installed three things that matter for this stage:

PackageWhat it is
dbt-core The dbt CLI itself. Provides the dbt command and the project-parsing engine.
dbt-duckdb The adapter that lets dbt talk to DuckDB. Each warehouse has its own adapter package — dbt-snowflake, dbt-bigquery, etc. You install the one that matches your warehouse.
duckdb The DuckDB engine itself. The adapter depends on it; we also use it directly in the verifier to inspect your warehouse.

Confirm everything is wired up:

dbt --version

You should see something like:

Core:
  - installed: 1.8.x
  - latest:    1.8.x

Plugins:
  - duckdb: 1.8.x

If dbt is not found, your virtualenv is not activated — run source .venv/bin/activate from the repo root and try again.

What dbt init does

dbt ships with a project generator. dbt init <name> creates a fresh directory tree with everything dbt expects:

dbt_project/
├── dbt_project.yml      ← project config: name, version, model paths, defaults
├── analyses/            ← ad-hoc SQL that doesn’t materialize
├── macros/              ← reusable Jinja-templated SQL snippets
├── models/              ← your transformations live here (this is where you spend most of your time)
├── seeds/               ← static CSVs loaded as tables (raw lookup data, jaffle_shop CSVs)
├── snapshots/           ← SCD2 history tables
├── tests/               ← custom singular SQL tests
└── README.md

Two files are missing from this list, on purpose:

  • profiles.yml — the connection config. Says which warehouse to use, where it lives, what credentials. By default dbt looks for it in ~/.dbt/profiles.yml (your home dir), but for this course we keep it inside dbt_project/ so the project is self-contained. You write it in the next exercise.
  • target/ — the build output (compiled SQL, manifests, run results). dbt creates this on the first dbt run; you never write to it by hand.

What you’ll do this stage

  1. Run dbt init dbt_project — scaffold the directory above.
  2. Write profiles.yml — tell dbt to use DuckDB at dev.duckdb in the project dir.
  3. Run dbt seed — load the three jaffle_shop CSVs into DuckDB as raw tables.
  4. Write your first model — stg_customers.sql, a SELECT from {{ ref('raw_customers') }}.
  5. Configure dbt_project.yml — default the staging models to the view materialization.

Everything you build under dbt_project/ is gitignored — the repo only ships the raw CSVs in data/. If you want to start over, run dbt-learn reset; the CLI deletes dbt_project/ and you’re back to a blank slate.

Common pitfalls

  • “dbt: command not found.” — Your venv is not activated. Run source .venv/bin/activate from the repo root.
  • Confusing dbt_project.yml with profiles.yml. — dbt_project.yml describes the project (paths, model defaults). profiles.yml describes the connection (which warehouse, which credentials). Project files travel with the repo; profiles can be machine-local. We bundle both inside dbt_project/ for this course because the warehouse is a local file.
  • Editing files in target/. — Don’t. target/ is regenerated on every dbt run. Your work lives in models/, seeds/, snapshots/, macros/, and tests/.
