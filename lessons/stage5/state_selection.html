State selection — rebuild only what changed

Every dbt build you’ve run so far has rebuilt the entire project. For 7 models that’s instant. For a real project with 500+ models, rebuilding everything every time you change one is wasteful — most CI systems take 10–30 minutes per dbt run on real-world projects, almost all of which is touching models that didn’t change.

state:modified+ is dbt’s solution. It compares the current project state against a previous state (a manifest from an earlier run) and selects only the models that differ — plus their downstream dependencies (+).

Why dbt is “stateless”… mostly

dbt is idempotent and stateless by design: running dbt build ten times in a row on the same project produces the same warehouse state every time. There’s no in-process memory of “what I did last time.”

But dbt does write artifacts — files in target/ that capture point-in-time state:

Artifact What it captures
target/manifest.json The parsed project: every model, source, test, macro, exposure with its config and dependencies
target/run_results.json The result of the most recent command: which nodes ran, how long they took, whether they passed
target/catalog.json Column-level metadata pulled from the warehouse via dbt docs generate

State selection works by comparing two manifests — the current one (in target/) against a previous one you point at via --state <path>. dbt walks every model node in the current manifest and asks “is this node different from the same node in the old manifest?” If yes, it qualifies for state:modified.

What “modified” actually means

A model is state:modified if any of these differ from the snapshot manifest:

  • The model’s SQL (file content)
  • The model’s config (materialization, unique_key, etc.)
  • The model’s schema (column-level YAML changes)
  • The model’s dependencies (upstream ref() calls changed)

Adding a comment to the SQL counts. Even a whitespace-only change counts. dbt is conservative — if the file’s hash differs, the model is modified.

The + suffix expands the set: state:modified+ includes the modified models and everything downstream of them. That’s what you want in CI: rebuild what changed and everything that depends on it.

The CI workflow

In production, the pattern is:

  1. Production main branch stores its target/manifest.json artifact somewhere (S3, a cache).
  2. A PR opens with a model change.
  3. CI runs: - Pull the production manifest into prev_target/. - Run dbt build --select state:modified+ --state ./prev_target.
  4. Only the changed model + downstream rebuild and test in the PR’s schema.
  5. PR merges, the new state becomes the next baseline.

Without state selection, every PR rebuilds the entire project — usually 90%+ unnecessary work.

What this exercise simulates

The seed-data project doesn’t have a real “previous state” to compare against. So the exercise simulates one:

  1. Run dbt build to produce a fresh target/manifest.json.
  2. Copy target/ to state_initial/ — this becomes the “previous build” snapshot.
  3. Modify dim_customers.sql so it differs from the snapshot.
  4. Run dbt run --select state:modified+ --state ../state_initial — dbt detects only dim_customers (and its downstream, if any) changed.

The verifier: - Confirms state_initial/manifest.json exists (proving you took the snapshot). - Confirms dim_customers.sql has the marker comment (proving you actually modified the file). - Runs the state-selection command itself and asserts it succeeds.

What you’ll see in the output

When the state-aware run executes, dbt logs something like:

01:23:45  Found 7 models, 1 snapshot, 1 analysis, 14 data tests, 1 seed, 3 sources, 477 macros
01:23:45  Concurrency: 1 threads (target='dev')
01:23:45  1 of 1 START sql table model main.dim_customers
01:23:45  1 of 1 OK created sql table model main.dim_customers
01:23:45  Finished running 1 table model in 0 hours 0 minutes ...

One model selected. One model run. Compare to a plain dbt build which would say 5 of 7 for the model count alone, plus tests and the seed.

Common pitfalls

  • Forgetting to take the snapshot before modifying. If state_initial/ doesn’t exist or has the same manifest as the current state, dbt’s state diff finds nothing and selects 0 models. The order matters: snapshot → modify → run.
  • Pointing --state at the current target/ instead of the snapshot. This is a no-op — comparing target/ to itself yields 0 differences. Always point --state at a separate directory.
  • Running dbt build (not dbt run) for the state-aware step. Both work — dbt build will run the modified models plus their tests. For this exercise, plain dbt run is fine; in production CI you’d typically use dbt build.
  • Putting state_initial/ inside dbt_project/. dbt’s clean command wipes target/ and dbt_packages/ from inside the project; state_initial/ could get caught in the cleanup. Keep it at the repo root, peer of dbt_project/.
