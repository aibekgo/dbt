dbt_utils — packages and pre-built macros

You wrote your first macro (cents_to_dollars) earlier in Stage 5. The dbt community has been writing useful macros for years; the most-used collection is dbt_utils, maintained by dbt Labs. It ships dozens of macros for common dbt patterns: surrogate keys, date spines, pivots, custom tests, and more.

This is the closing exercise of Stage 5 — a quick tour of how to install a package and use one of its macros.

How packages work

dbt’s package system is conceptually simple: a packages.yml file at the root of your dbt project lists the packages you want, and dbt deps clones them into dbt_packages/ (peer of models/, macros/, etc.).

# dbt_project/packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]

Three forms of version::

  • Pinned: version: 1.1.0 — exactly that version
  • Range: version: [">=1.1.0", "<2.0.0"] — most common; pins to a major
  • Latest: omit version: — risky, breaks reproducibility

After editing packages.yml, you run dbt deps:

dbt deps

dbt clones the package into dbt_packages/dbt_utils/. Every macro inside that directory becomes callable from any model, prefixed by the package name.

Calling a packaged macro

Once installed, dbt_utils.generate_surrogate_key(...) is callable from any model file:

select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'customer_id']) }} as order_key,
    ...

The dot-separated form (<package>.<macro>) disambiguates from same-named macros in your own project. Without it, dbt couldn’t tell whether generate_surrogate_key was yours or a package’s.

What generate_surrogate_key does

It takes a list of column names and returns a deterministic hash that’s:

  • Unique per combination — different column values → different hash
  • Stable across runs — same input → same hash forever
  • Warehouse-portable — uses MD5 by default; works on Snowflake, BigQuery, DuckDB, Postgres

It compiles to something like:

md5(cast(coalesce(cast(order_id as text), '') || '-' || coalesce(cast(customer_id as text), '') as text)) as order_key

The coalesce(..., '') and '-' separator handle nulls and prevent collisions like ('1', '23') and ('12', '3') mapping to the same hash.

When you’d actually need it

Real use case: a fact table whose natural primary key is a combination of columns rather than a single one. Examples:

  • fct_session_events: PK is (session_id, event_sequence) — combine into a session_event_key
  • fct_invoice_lines: PK is (invoice_id, line_number) — combine into a line_key
  • dim_employee_assignments: PK is (employee_id, role_id, effective_date)

For our fct_orders, order_id is already a single-column PK, so a surrogate key is structurally redundant — but the exercise still demonstrates the install + call flow.

dbt_project/
├── dbt_packages/

│       │   ├── sql/
│       │   └── ...
│       └── models/
│           └── ...
├── packages.yml
├── ...

dbt_packages/ is gitignored in this project (and dbt-Labs’s own dbt_project.yml adds it to clean-targets). You commit packages.yml; CI runs dbt deps to materialize the install.

Common pitfalls

  • Forgetting dbt deps after editing packages.yml. Just adding the package to YAML doesn’t install anything. Run dbt deps after every edit.
  • Calling a macro without the package prefix. {{ generate_surrogate_key(...) }} (no prefix) only works if you’ve defined a local macro by that name. Package macros need {{ dbt_utils.generate_surrogate_key(...) }}.
  • Pinning to a too-old version. dbt_utils got renamed (a long time ago) — dbt-labs/dbt_utils is the modern path. Old fishtown-analytics/dbt_utils references break.
  • Committing dbt_packages/ to git. Big and reproducible from packages.yml, so it’s wasted bytes. Confirm .gitignore includes dbt_packages/ (in this project, dbt_project/ itself is ignored, so it’s covered).
