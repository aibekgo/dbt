first_macro — write cents_to_dollars and refactor stg__payments

stg__payments.sql currently has the cents→dollars conversion inline:

select
    id              as payment_id,
    order_id,
    payment_method,
    amount / 100.0  as amount
from {{ source('stripe', 'raw_payments') }}

That’s fine for one model. The problem starts when another model — say a future stg__refunds or stg__chargebacks — needs the same conversion. Copy-paste means three places to update if the rounding policy ever changes. A macro centralizes the logic so it’s defined once and called everywhere.

How the macro and the refactor fit together

The walkthrough below has the full files. Two pieces:

  • A new macros/cents_to_dollars.sql that wraps the body round( 1.0 * {{ column_name }} / 100, {{ decimal_places }} ) in a {% macro %} block with decimal_places=2 as the default. The opening -%} and closing {%- strip whitespace so the macro expands as a clean inline expression.
  • An edit to stg__payments.sql swapping amount / 100.0 for {{ cents_to_dollars('amount') }} as amount. The 'amount' is a string — the name of the column the macro should operate on — which the macro drops verbatim into the rendered SQL.

After dbt compiles, the line reads round( 1.0 * amount / 100, 2 ) as amount. The 1.0 coefficient forces float math, and round(..., 2) constrains decimal places. Slightly more polished than the original; functionally equivalent for the seed data.

What dbt does at parse time

When you run dbt parse (or any command that triggers parsing), dbt:

  1. Scans macros/ and finds cents_to_dollars in cents_to_dollars.sql.
  2. Registers it in target/manifest.json under macros.macro.dbt_project.cents_to_dollars.
  3. Walks every model file. When it finds {{ cents_to_dollars('amount') }} in stg__payments.sql, it substitutes the macro’s body with column_name='amount' and decimal_places=2.
  4. Writes the rendered SQL to target/compiled/dbt_project/models/staging/stg__payments.sql.

That compiled file is what the warehouse actually sees — {{ cents_to_dollars('amount') }} is gone, replaced by round( 1.0 * amount / 100, 2 ). The Jinja layer is purely a preprocessor.

How to verify the refactor is faithful

The macro should produce the same dollar values as the original amount / 100.0. The verifier checks this indirectly:

  • The model still compiles and runs.
  • 113 payment rows still have amount > 0 and amount < 100 — meaning the conversion happened (cents like 2600 would be > 100, dollars like 26.00 are < 100).

The downstream int_order_payments and fct_orders use sum(amount) and coalesce(p.total_amount, 0) as amount respectively, so the aggregate dollar amounts in those models also stay constant if the refactor is correct.

Common pitfalls

  • Calling the macro without quotes around the column name. {{ cents_to_dollars(amount) }} (no quotes) would try to look up a Python variable amount, fail, and error at parse time. Use {{ cents_to_dollars('amount') }} — pass the column name as a string.
  • Putting the macro inside the model file. {% macro %} blocks technically work inline, but dbt only registers them as project macros if they live under macros/. Keep one file per macro under macros/.
  • Forgetting the whitespace-control dashes. Without -%} and {%-, the macro expands across multiple lines and the compiled SQL has awkward gaps. Inline expressions like this one read better with whitespace stripped.

Steps — exercise walkthrough

1. From the repo root, create the macro file:

mkdir -p dbt_project/macros
touch dbt_project/macros/cents_to_dollars.sql

2. Paste this into cents_to_dollars.sql:

{% macro cents_to_dollars(column_name, decimal_places=2) -%}
round( 1.0 * {{ column_name }} / 100, {{ decimal_places }} )
{%- endmacro %}

The macro: - Takes column_name (positional, required) and decimal_places (positional with default 2). - Renders to a SQL expression: round( 1.0 * <col> / 100, <decimal_places> ). - The leading -%} and trailing {%- strip whitespace so the expansion is one clean inline expression.

3. Open dbt_project/models/staging/stg__payments.sql. Replace the inline amount / 100.0 with a macro call. The full file should read:

select
    id                                  as payment_id,
    order_id,
    payment_method,
    {{ cents_to_dollars('amount') }}    as amount
from {{ source('stripe', 'raw_payments') }}

The first argument is the column name as a string: 'amount', with quotes.

4. Re-run the staging model to materialize against the macro:

cd dbt_project
dbt run --select stg__payments

You should see one green line. Behind the scenes, dbt rendered the macro into round( 1.0 * amount / 100, 2 ) and used that as the column expression.

5. Inspect the compiled SQL to confirm the macro expanded:

cat target/compiled/dbt_project/models/staging/stg__payments.sql

The {{ cents_to_dollars('amount') }} line is gone; in its place is round( 1.0 * amount / 100, 2 ).

6. Sanity-check the dollar values look right:

duckdb ../database/dev.duckdb -c "select payment_id, amount from stg__payments limit 5"

Five rows, amount values like 1.00, 26.00, 1.50 — dollars, not cents.

7. Press v to verify.

What the verifier checks

  • dbt run --select stg__payments exits 0.
  • target/manifest.json registers a macro named cents_to_dollars.
  • select count(*) from stg__payments where amount > 0 and amount < 100 returns 113 — meaning all 113 payments are now in dollar units (not cents).

Common failure modes

Symptom Fix
Compilation Error: macro 'cents_to_dollars' is undefined The macro file isn’t in dbt_project/macros/ or its filename doesn’t end in .sql. Confirm the path: dbt_project/macros/cents_to_dollars.sql.
Macrocents_to_dollarsnot found in target/manifest.json The macro file exists but didn’t parse — usually a syntax error in the Jinja. Common cause: missing {% endmacro %} or a typo like {% macro %} (no name).
Compilation Error: '<class ...>' object has no attribute 'amount' (or similar attribute error) You wrote {{ cents_to_dollars(amount) }} without quotes. The argument must be a string: 'amount'.
count(*) where amount > 0 and amount < 100 returns 0 or wrong number The cents → dollars conversion didn’t happen. Check that the macro body has / 100 (not * 100) and that you replaced the original expression rather than adding another column.
Stage 3 tests fail (e.g. not_null on payment_id) Unrelated — the refactor didn’t touch the column shape. Check you didn’t accidentally drop columns from the select list.
