Analyses — SQL that compiles but doesn’t materialize

Models, tests, and seeds all do something in the warehouse — they create tables, run assertions, load data. Analyses are the odd cousin: they’re SQL files in your dbt project that get compiled but never run as a build step.

What an analysis is for

An analysis is the right home for SQL that you want to:

  • Version alongside your dbt code so the team can review it in PRs
  • Use ref() and macros so it stays in sync with the rest of the project
  • Compile to runnable SQL that you (or a BI tool, or a one-off cron) can paste into a query editor
  • Not materialize as a table or view — because it’s a one-off, an audit, or a teaching example

Concrete examples:

  • Top-N reports that should be run on demand, not nightly. “Top 10 customers by lifetime revenue.”
  • Audit queries flagging suspicious rows. “Orders with payment_count = 0 that are still marked completed.”
  • Migration validation queries comparing old and new versions of a fact table side by side.
  • Training queries that show a new analyst how to construct a particular cohort.

The common thread: valuable SQL, but not part of the production data flow.

Where they live and what dbt compile does

Analyses go in dbt_project/analyses/ (the folder is part of the default scaffold).

When you run:

dbt compile --select top_customers_by_revenue

dbt does this:

  1. Parses the project to build the manifest. The analysis shows up as a node with resource_type = "analysis".
  2. Renders the Jinja in your analysis SQL — ref(), source(), macros, {% if %} blocks all get evaluated.
  3. Writes the result to target/compiled/<project>/analyses/<analysis_name>.sql.

That’s it. No create table, no create view, nothing in DuckDB. The output is a flat .sql file you can copy-paste anywhere.

dbt run skips analyses entirely — they don’t materialize, so there’s nothing for dbt run to do. Likewise dbt build. The only way to exercise an analysis is dbt compile.

Why not just write a model?

You could materialize the top-customers query as a view:

{{ config(materialized='view') }}

select ... from {{ ref('fct_orders') }} ...
limit 10

It works, but it costs you on three axes:

Axis Model Analysis
Lives in the warehouse Yes — view or table No — only in target/compiled/
Runs on every dbt run Yes No
Counted in your DAG / docs as production output Yes — surfaces in lineage Yes, but as a separate analysis node
limit semantics “Top 10 ever” — view stale unless re-run “Top 10 right now” — query is run on demand

The deciding question: is this query part of the production data product, or is it ad-hoc? Production = model. Ad-hoc but worth keeping = analysis.

Compiled output you can actually run

After dbt compile, target/compiled/dbt_project/analyses/top_customers_by_revenue.sql looks like this (Jinja resolved):

select
    c.customer_id,
    c.first_name,
    c.last_name,
    count(o.order_id) as order_count,
    sum(o.amount)     as lifetime_revenue
from "main"."fct_orders" o
join "main"."dim_customers" c using (customer_id)
group by 1, 2, 3
order by lifetime_revenue desc
limit 10

That’s drop-in pasteable into the DuckDB CLI, a BI tool, or anywhere else that speaks SQL. The {{ ref(...) }} references have been resolved to fully-qualified table names.

Common pitfalls

  • Putting a {{ config(...) }} block in an analysis. Analyses don’t materialize; the config is silently ignored, but it’s a sign the file is in the wrong folder. If you find yourself wanting materialized='table', move the file to models/.
  • Calling it analysis/ (singular). The default config is analysis-paths: ["analyses"] (plural). The folder name is plural; the resource type in the manifest is analysis (singular). Don’t conflate.
  • Forgetting dbt compile runs the entire project by default. Without --select, you’ll compile every analysis and every model in the project. Scope with --select <name> while iterating to keep the feedback loop fast.
