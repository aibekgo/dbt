Singular tests — when no built-in fits

The four built-in generic tests cover most pure column-level assertions. But sooner or later you’ll have a rule that doesn’t fit the mold. Examples:

  • Total payment amount on an order should never be negative.
  • Refund timestamps should always be later than the original payment timestamp.
  • No customer should appear in dim_customers without at least one matching row in stg__orders.

These are business rules, not column shape rules. They depend on the relationship between rows, on derived values, or on assertions that span tables. There’s no dbt-utils.no_negative_payments test off the shelf. You write them yourself, as singular tests.

What a singular test looks like

A singular test is a .sql file in the tests/ folder. Inside is a plain select statement. The rule is:

A singular test passes when the query returns 0 rows. It fails when the query returns ≥ 1 row.

That’s the whole contract. You write the SQL that finds the bad rows. dbt runs it, counts the rows, and decides pass/fail based on the count.

For our project, here’s a useful one — payments shouldn’t have negative totals:

-- dbt_project/tests/assert_no_negative_payment_totals.sql
select order_id, total_amount
from {{ ref('int_order_payments') }}
where total_amount < 0

Read it as the assertion “there should be no rows where total_amount is negative.” If the staging logic ever miscounts and produces a negative dollar total, this test catches it. If everything’s well-behaved, the query returns 0 rows and the test passes silently.

Where it lives and what dbt does with it

Path Meaning
dbt_project/tests/assert_no_negative_payment_totals.sql The file you write
target/run_results.json after dbt test Records the pass/fail status
target/compiled/dbt_project/tests/... Where dbt puts the rendered SQL after compile

dbt’s test-paths: config (default tests) tells it where to look. Anything ending in .sql under there is treated as a singular test. The filename becomes the test’s unique_id, so use a descriptive name — assert_no_negative_payment_totals is much better than test_1.sql.

Selecting just singular tests

When you have both kinds of tests in a project, you can scope to one or the other:

dbt test --select test_type:singular   # only the .sql files in tests/
dbt test --select test_type:generic    # only the YAML-attached tests

test_type: is one of dbt’s built-in selectors. Most teams don’t use it day-to-day — dbt test runs all kinds together — but it’s useful for debugging a singular test in isolation.

When to reach for a singular test

The decision tree is short:

  1. Can a built-in (unique, not_null, accepted_values, relationships) cover this? Use that.
  2. Does a package like dbt-utils or dbt-expectations already have a test for this shape? Use that.
  3. Otherwise, write a singular test.

Singular tests aren’t reusable across models — that’s their main weakness. If you find yourself writing the same pattern twice (e.g. “this column’s sum should match that column’s sum across two models” on two different model pairs), it’s time to convert it into a custom generic test (a Jinja macro under tests/generic/). That’s a Stage 5+ topic.

Common pitfalls

  • select * returning every row. Forgetting the where clause means the test always finds bad rows and always fails. Always include the predicate that defines what “bad” looks like.
  • Inverting the polarity. New writers sometimes write the positive condition: where total_amount >= 0 (the rows you want). That returns mostly all rows and fails forever. The query has to find the violations, the rows that shouldn’t exist.
  • Hard-coding the schema name. Always use {{ ref('int_order_payments') }} — never main.int_order_payments. The ref() makes the test depend on the model in the DAG, so dbt knows to build the model first when you run dbt build.

Exercise walkthrough

Steps

1. From the repo root, create the test file:

mkdir -p dbt_project/tests
touch dbt_project/tests/assert_no_negative_payment_totals.sql

The tests/ folder may already exist (it’s part of the default dbt init scaffold) — mkdir -p is harmless either way.

2. Paste this into assert_no_negative_payment_totals.sql:

-- A singular test passes when this query returns 0 rows.
-- We're asserting that no order has a negative total_amount.
select order_id, total_amount
from {{ ref('int_order_payments') }}
where total_amount < 0

Three things to notice:

  • select finds the bad rows, not the good ones. The query returns rows that violate the assertion. 0 rows = test passes.
  • {{ ref('int_order_payments') }} not raw table name. This wires the test into the DAG so dbt builds the model before running the test in dbt build.
  • where total_amount < 0 — strict inequality. Zero is allowed (a refunded order can sum to 0); only negative amounts are violations.

3. Run just the singular tests:

cd dbt_project
dbt test --select test_type:singular

You should see one test execute and pass:

Completed successfully

Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1

4. Confirm it shows up in the manifest:

dbt ls --resource-type test --select test_type:singular

One line: dbt_project.assert_no_negative_payment_totals.

5. (Optional, just to see the failure path.) Temporarily flip the predicate to where total_amount > 0 and re-run dbt test --select test_type:singular. You should see a FAIL with the count of rows the test found. Flip it back to < 0 before pressing v.

6. Press v to verify.

What the verifier checks

  • dbt test --select test_type:singular exits 0 with at least one test running and passing.

Common failure modes

Symptom Fix
Compilation Error: dbt found 0 tests of type singular The file isn’t in tests/, or it doesn’t end in .sql. Confirm path is exactly dbt_project/tests/assert_no_negative_payment_totals.sql.
Compilation Error: 'int_order_payments' is undefined You wrote from int_order_payments (raw name) instead of from {{ ref('int_order_payments') }}. The ref() is required.
Test reports FAIL N Either the predicate is inverted (> 0 instead of < 0 — finds the good rows) or the upstream data legitimately has a negative total (shouldn’t happen with the seed data).
Database Error: Catalog Error: Table with name int_order_payments does not exist! The intermediate model isn’t built yet. Run dbt run --select int_order_payments first, or use dbt build --select int_order_payments+ to build the chain and run the test together.
