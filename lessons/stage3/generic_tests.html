Generic tests — unique, not_null, and where descriptions live

Time to write your first tests. The tests_intro lesson covered the why; this one covers the file — what _models.yml looks like, where it sits, and how a test ends up attached to a column.

The schema YAML

Every staging model deserves a YAML entry that documents what it represents and asserts the data shape. The conventional file is models/staging/_models.yml:

version: 2

models:
  - name: stg__customers
    description: "One row per customer from the Jaffle Shop application database."
    columns:
      - name: customer_id
        description: "Surrogate primary key from raw_customers.id."
        tests:
          - unique
          - not_null
      - name: first_name
      - name: last_name

Three things to notice:

  1. version: 2 at the top — this isn’t your project version, it’s dbt’s schema-YAML format version. Required.
  2. models: is a list. One entry per model file in the folder. The name: must match the SQL file’s basename (no .sql extension).
  3. tests: under a column attaches generic tests to that column. Each test name is one of dbt’s built-ins or a package-supplied one. unique and not_null are the most common; accepted_values and relationships come in the next exercise.

Descriptions, side by side with tests

When you’re already touching the YAML to add tests, add descriptions too. They cost nothing (one line per field) and pay back twice:

  • The docs site picks them up. dbt docs generate reads description: and surfaces it next to the column in the lineage view. Your future-self looking at the docs page will thank you.
  • Reviewers can sanity-check intent. A description like “Surrogate primary key from raw_customers.id” tells the next person reading the YAML what unique is asserting and why.

You don’t have to fill in every column. Top-priority descriptions: the model itself, the primary key, any foreign keys, anything with a non-obvious meaning (like status enums).

What dbt test --select staging does

After saving the YAML, run:

cd dbt_project
dbt test --select staging

dbt does this:

  1. Parses the project (rebuilds target/manifest.json) and finds every test attached to a model in models/staging/.
  2. For each test, generates the SQL that returns bad rows — e.g. for unique on customer_id: sql select customer_id from "main"."stg__customers" group by customer_id having count(*) > 1
  3. Executes each query. If a query returns 0 rows, the test passes. If it returns ≥1 rows, dbt prints how many bad values it found and the run fails.

If the staging models are clean (they should be — they’re 1:1 with the source CSVs and the CSVs are deterministic), every test passes.

Cardinality vs grain — a quick reminder

The reason unique matters on staging keys is that it’s the contract for downstream joins. fct_orders joins stg__orders to stg__customers on customer_id. If customer_id weren’t unique in stg__customers, that join would multiply rows and fct_orders would silently inflate.

A unique test is the cheapest way to catch that the moment it happens. One YAML line is worth a week of debugging “why is revenue suddenly 2.3× what it should be.”

Common pitfalls

  • Putting tests at the model level instead of the column level. Generic tests attach to a column, not a model. They go under columns: - name: <col> tests:, not directly under the model.
  • Forgetting version: 2. dbt will refuse to parse the file and the error message is cryptic. Always start the file with version: 2.
  • Naming the file inconsistently. _models.yml, schema.yml, models.yml — dbt accepts any of them as long as it’s under model-paths. The leading underscore convention is just for sort order.

Exercise walkthrough

Steps

1. From the repo root, create a new file at dbt_project/models/staging/_models.yml with this content:

version: 2

models:
  - name: stg__customers
    description: "One row per customer from the Jaffle Shop application database."
    columns:
      - name: customer_id
        description: "Surrogate primary key from raw_customers.id."
        tests:
          - unique
          - not_null
      - name: first_name
      - name: last_name

  - name: stg__orders
    description: "One row per order placed in the Jaffle Shop app."
    columns:
      - name: order_id
        description: "Primary key, renamed from raw_orders.id in staging."
        tests:
          - unique
          - not_null
      - name: customer_id
        description: "Foreign key to stg__customers.customer_id."
        tests:
          - not_null
      - name: status
        description: "Order lifecycle state. Constrained to a known set in the next exercise."

  - name: stg__payments
    description: "One row per payment event from Stripe (cents converted to dollars in staging)."
    columns:
      - name: payment_id
        description: "Primary key, renamed from raw_payments.id in staging."
        tests:
          - unique
          - not_null
      - name: order_id
        description: "Foreign key to stg__orders.order_id."
        tests:
          - not_null

2. From inside dbt_project/, run the tests:

cd dbt_project
dbt test --select staging

You should see seven tests run and pass:

Completed successfully

Done. PASS=7 WARN=0 ERROR=0 SKIP=0 TOTAL=7

(Three unique tests on the three primary keys, plus four not_null tests on customer_id/order_id/payment_id/stg__orders.customer_id.)

3. Sanity-check that the manifest sees the tests:

dbt ls --resource-type test --select staging

You should see seven lines like dbt_project.unique_stg__customers_customer_id, etc.

4. Press v to verify.

What the verifier checks

  • dbt test --select staging exits 0 and every test passes.
  • target/manifest.json shows at least 2 tests on stg__customers (specifically unique and not_null).
  • At least 2 tests on stg__orders.
  • At least 2 tests on stg__payments.

The verifier is checking the tests are declared, not just that the YAML file exists. If you put the tests at the wrong YAML level (e.g. directly under the model instead of under a column), the count check will fail with a clear message.

Common failure modes

Symptom Fix
Compilation Error: Invalid version 'version' formodels.yml`` Missing version: 2 at the top. Required for every schema YAML.
