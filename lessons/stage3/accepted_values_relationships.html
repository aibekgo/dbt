accepted_values and relationships — the other two built-ins

unique and not_null are the workhorses of generic testing — almost every primary key gets both. The other two built-in tests, accepted_values and relationships, fire less often but catch a different class of bug. This exercise wires up one of each.

accepted_values — enum-style assertions

Every business has columns that should only ever hold a fixed set of values. Order status, subscription tier, country code, payment method. When something outside that set shows up — a typo ("shippeed"), a new value the warehouse forgot to handle ("refund_pending") — every downstream filter that says where status = 'shipped' silently misses it.

accepted_values is the assertion: “the only legal values for this column are X, Y, Z.” Anything else fails the test.

- name: status
  tests:
    - accepted_values:
        values: [placed, shipped, completed, return_pending, returned]

Note the indentation — accepted_values takes arguments, so it’s a YAML mapping (accepted_values: {values: [...]}), not just a name like unique. Same for relationships.

When a new status appears upstream, this test fires the next time dbt test runs. You either: - update the list (the new status is legitimate) - or fix the data (the new status is a typo or a vendor mistake)

Either way, you find out the day it lands instead of the day a quarterly report is wrong.

relationships — foreign-key integrity

dbt models live in a warehouse, and warehouses don’t enforce foreign keys. If you point a join at customer_id in fct_orders, nothing stops a row from sneaking in where the customer_id doesn’t exist in dim_customers. The join silently drops it (with inner join) or returns nulls (with left join).

relationships is the test that says “every value in this column must exist in the referenced model’s column.”

- name: customer_id
  tests:
    - relationships:
        to: ref('dim_customers')
        field: customer_id

The arguments are: - to: — a ref() to the model that holds the parent table. - field: — the column in that parent table the value must appear in.

When the test runs, dbt generates SQL roughly equivalent to:

select customer_id from "main"."fct_orders"
where customer_id is not null
  and customer_id not in (select customer_id from "main"."dim_customers")

If that returns 0 rows, every customer_id in fct_orders is accounted for. If not, you have orphan rows — usually a sign that one staging model is filtering out customers the other one didn’t.

Where these go

The new tests land in two places:

  • models/staging/_models.yml — extend the status column on stg__orders with accepted_values.
  • models/marts/_models.yml — a new file, peer of the staging one, declaring fct_orders and its tests.

The marts/ folder didn’t have a YAML file before because Stage 2 didn’t add one. That’s normal — every layer eventually gets its own _models.yml once you start documenting and testing the models in it.

Why this catches bugs unique doesn’t

unique and not_null only assert things about a column in isolation. They can’t tell you that fct_orders.customer_id is a real customer; they can only tell you that it’s set and non-duplicated.

relationships is the cross-model assertion. It enforces the invariants that the warehouse won’t enforce for you. Combined with unique on the parent’s customer_id, it gives you the foreign-key safety net a transactional database would. Without one or both, you’re trusting that joins behave — and joins are exactly where data quietly goes wrong.

Common pitfalls

  • relationships syntax: to: 'dim_customers'. This silently passes parsing in older dbt versions but doesn’t compile to a real reference. Use to: ref('dim_customers') — that’s a Jinja expression dbt evaluates.
  • Putting accepted_values at the column level without the values: key. accepted_values requires arguments. The bare form - accepted_values will parse but fail at run time with a confusing error. Always include values: [...].
  • Listing values that don’t actually exist. If your status column has 'returned' but you list 'return' in accepted_values, every 'returned' row will fail the test. The lesson includes the canonical list for jaffle_shop — copy it exactly.
