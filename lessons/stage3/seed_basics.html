Seeds — small reference data, committed to git

dbt has three ways to get raw data into the warehouse:

  1. Sources — tables that already exist in the warehouse, landed by an external loader (Fivetran, Airbyte, a Python script). dbt only declares them; it doesn’t load them.
  2. Seeds — small CSVs you commit to the dbt project under seeds/. Running dbt seed loads each CSV into the warehouse as a table.
  3. Stage 1’s path — a Python ingestion script that writes directly to DuckDB outside of dbt entirely.

Stage 1 of this course used option 3 — scripts/ingest_raw.py lands the jaffle_shop CSVs into DuckDB, and Stage 2 declared them as sources. That’s the right pattern for primary data: large, frequently changing, and pulled from an upstream system you don’t control.

This exercise introduces option 2 — seeds — for the use case it’s actually best at: small reference tables that change rarely and are versioned with your dbt code.

When to reach for a seed

The decision tree is short:

Data fits this description Use
Small (≤ a few thousand rows), changes rarely, you’d hand-edit the CSV Seed
Large or frequently changing, comes from an external system Loader (Fivetran, Airbyte, custom script) → Source
Generated by an upstream model in dbt itself Just a regular model

Classic seed candidates:

  • Country code → country name lookups
  • Currency exchange rates frozen at month-end
  • Marketing campaign → campaign type mapping
  • Status code → human-readable description

For the jaffle_shop project, the natural seed is a status-description table: the five values placed / shipped / completed / return_pending / returned mapped to a sentence the BI tool can put on a dashboard.

What dbt seed does

When you run dbt seed:

  1. dbt scans seed-paths: (default: seeds/).
  2. For each .csv it finds, it infers column types from the first ~1000 rows (DuckDB’s default), runs create or replace table seed_name as select ..., and writes the rows.
  3. After the seed finishes, the table is queryable like any other dbt-built relation. ref('order_status_descriptions') works.

Compared to Stage 1’s Python ingestion:

Python ingestion (scripts/ingest_raw.py) Seed (dbt seed)
Triggered by Custom command outside dbt dbt seed (and runs as part of dbt build)
Lives in A Python script A CSV in seeds/
Versioned in git The script is, the data isn’t The CSV itself is in git
Best for Large pipeline-style loads, refreshable Small, slow-changing reference data
Diffs cleanly in PRs No — script is procedural Yes — CSV diffs are line-by-line

The CSV-in-git story is the killer feature. When marketing sends a new mapping for campaign_id → campaign_type, you bump the CSV in a PR, the diff shows exactly what changed, the deploy of the dbt project re-runs dbt seed, and the new mapping is live the next morning.

Same ref() machinery

Once seeded, the table behaves identically to any model. Downstream models reference it with ref():

select
    o.order_id,
    o.status,
    d.description as status_description
from {{ ref('stg__orders') }} o
left join {{ ref('order_status_descriptions') }} d using (status)

It shows up in the DAG as a green-bordered node (a slightly different shade from sources, in the dbt docs UI). Tests can attach to it via the same _models.yml mechanism.

Common pitfalls

  • Treating seeds as a data-loading tool. Seeds aren’t for raw data, even if it’s only a few hundred MB. They live in git and get loaded on every dbt seed. Anything ingestion-shaped belongs in a real loader.
  • Over-formatting the CSV. dbt seed infers column types from the data. A CSV with stray quotes, trailing commas, or BOM headers will produce confused types. Keep the CSV plain: comma-separated, double-quoted strings only when they contain commas, no extra whitespace.
  • Forgetting dbt seed in CI. A model that ref()s a seed will fail in a fresh environment if the seed wasn’t built first. dbt build handles this (it runs seeds before models in DAG order); plain dbt run will only build models, not seeds. If you suddenly hit “Catalog Error: Table with name order_status_descriptions does not exist” in CI, check whether dbt seed is wired in.

Exercise walkthrough

Steps

1. From the repo root, create the seed file at dbt_project/seeds/order_status_descriptions.csv with this content:

status,description
placed,Order has been placed but not yet shipped
shipped,Order has shipped to the customer
completed,Order delivered and confirmed received
return_pending,Customer has indicated a return; awaiting receipt
returned,Item has been returned to the warehouse

Five rows. The status column matches the values the accepted_values test from the previous exercise constrains stg__orders.status to.

2. Run the seed loader:

cd dbt_project
dbt seed --select order_status_descriptions

You should see one green line:

1 of 1 OK loaded seed file main.order_status_descriptions

The --select is optional — bare dbt seed would load every CSV in seeds/. Scoping is just faster while developing.

3. Confirm the table exists in DuckDB:

duckdb ../database/dev.duckdb -c "select count(*) from order_status_descriptions"

Should print 5.

4. Peek at the data:

duckdb ../database/dev.duckdb -c "select * from order_status_descriptions"

Five rows with the descriptions you wrote. Notice DuckDB inferred status and description as VARCHAR automatically — dbt seed reads the CSV header for column names and the first batch of rows for types.

5. Press v to verify.

What the verifier checks

  • dbt seed --select order_status_descriptions exits 0.
  • Table order_status_descriptions exists in dev.duckdb.
  • select count(*) from order_status_descriptions returns exactly 5.

Common failure modes

Symptom Fix
Encountered an error: Could not find any seeds named like 'order_status_descriptions' The CSV isn’t where dbt expects. Confirm the path is exactly dbt_project/seeds/order_status_descriptions.csv (the filename minus .csv becomes the seed name).
Row count is 6 not 5 One too many rows in the CSV — the header row counts as a row in the file but not in the table. Five status descriptions = 5 data rows + 1 header line = 6 lines total.
Row count is 4 Missing one of the five statuses, or an extra blank line. CSVs with trailing whitespace lines silently drop the last data row in some parsers.
column "status" mentioned in CHECK constraint does not exist The column header doesn’t match. Confirm the first line of the CSV reads exactly status,description with no spaces around the comma.
