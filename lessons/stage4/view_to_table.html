Override the folder default — make int_order_payments a table

Right now int_order_payments is a view. Why? Because dbt_project.yml only configures staging: and marts: materializations — intermediate/ has no entry, so it falls back to dbt’s built-in default, which is view.

A 99-row aggregation of payments is too small to care about either way, but the exercise matters: this is how you tell dbt to build one specific model differently from its folder peers.

The override mechanism

dbt resolves a model’s materialization by checking these places in order, latest wins:

  1. dbt’s built-in default → view
  2. dbt_project.yml’s models: dbt_project: <folder>: +materialized: <type>
  3. {% config %} inside a YAML schema file
  4. {{ config(materialized='...') }} at the top of the model’s SQL file

The fourth — the inline SQL config — is the one used most. It lives next to the model so readers can see the choice without hunting through other files.

{{ config(materialized='table') }}

select ...

The {{ config(...) }} call must be at the top of the file, before the select. dbt’s parser scans models for these calls before executing anything, so config() doesn’t behave like a normal Jinja expression — it’s metadata, not output.

What changes after this exercise

Three things, all visible:

  • target/manifest.json — nodes."model.dbt_project.int_order_payments".config.materialized flips from "view" to "table".
  • dev.duckdb — select table_type from information_schema.tables where table_name='int_order_payments' returns BASE TABLE instead of VIEW.
  • The next time you run dbt run --select int_order_payments, dbt issues create or replace table ... as select ... instead of create or replace view ... as .... The compiled SQL is the same; the wrapper SQL changes.

The verifier checks all three.

Why this would matter on real data

99 payment rows aggregated to 99 order rows is a no-op for performance. But the same int_order_payments shape on 100 million payment rows aggregated to 80 million orders is expensive to recompute on every BI query that touches fct_orders (because a view re-runs its query at every read). Switching to table means dbt pays the aggregation cost once per dbt build, and every query downstream reads pre-aggregated rows.

The decision rule: if the SQL behind a view is slow and the result is queried often, promote it to a table.

Common pitfalls

  • Putting {{ config(materialized='table') }} below the select. It’s just inert text there. Always at the top of the file.
  • Editing dbt_project.yml to add an intermediate: block instead of using {{ config() }}. Both work, but they mean different things — the project-yml route changes the default for every model in the folder, while the inline route changes just one. For one model, prefer the inline route; if you find yourself wanting most intermediates as tables, then the project-yml route makes sense.
  • Forgetting to actually run dbt run after editing the file. Just changing the SQL doesn’t update the warehouse — dbt doesn’t watch for file changes. The warehouse only catches up when you re-run.

Steps — exercise walkthrough

1. Open dbt_project/models/intermediate/int_order_payments.sql. Add a config block as the very first thing in the file:

{{ config(materialized='table') }}

select
    order_id,
    sum(amount)              as total_amount,
    count(*)                 as payment_count
from {{ ref('stg__payments') }}
group by order_id

The select stays exactly as it was. Only the config block at the top is new.

2. Re-run the model so the warehouse catches up:

cd dbt_project
dbt run --select int_order_payments

You should see one green line. dbt issued create or replace table main.int_order_payments as select ... instead of create or replace view.

3. Confirm the warehouse object changed shape:

duckdb ../database/dev.duckdb -c "select table_type from information_schema.tables where table_name='int_order_payments'"

Should print BASE TABLE. Before this exercise it printed VIEW.

4. (Optional but useful.) Inspect the manifest:

duckdb -c "select * from read_json('target/manifest.json')" | grep -i int_order_payments

Or open target/manifest.json and search for the int_order_payments node — config.materialized is now "table".

5. Press v to verify.

What the verifier checks

  • dbt run --select int_order_payments exits 0.
  • target/manifest.json shows int_order_payments materialized as table.
  • information_schema.tables reports table_type = 'BASE TABLE'.

Common failure modes

Symptom Fix
Model 'int_order_payments' is materialized as 'view', expected 'table' The {{ config(...) }} block isn’t being picked up. Two common causes: (a) you put it below the select instead of at the top of the file, or (b) the syntax has a typo (materialized='table' — single quotes around table, the = has no spaces in idiomatic dbt code, but spaces don’t actually break it).
Compilation Error: 'config' is not callable Spelling. Must be {{ config(materialized='table') }} exactly — config, lowercase, with parentheses.
int_order_payments.table_type is still VIEW dbt builds against the warehouse, but you ran the verifier without re-running the model. Run dbt run --select int_order_payments first, then v.
Catalog Error: Table with name int_order_payments already exists! (rare) Stale state — usually fixed by dbt run --select int_order_payments --full-refresh which forces a drop-and-recreate.
