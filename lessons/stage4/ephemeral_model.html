Ephemeral models — inlined as CTEs, never persisted

The view_to_table exercise made int_order_payments more present in the warehouse — a real table you can query directly. This exercise does the opposite: makes it disappear from the warehouse entirely. After this change, select * from int_order_payments in DuckDB returns “table not found”. Yet fct_orders still works perfectly.

That’s ephemeral.

What ephemeral actually does

When you set {{ config(materialized='ephemeral') }} on a model, dbt does not issue any DDL for it. There’s no create view, no create table, no warehouse object. Instead, every time a downstream model says {{ ref('the_ephemeral') }}, dbt inlines the ephemeral’s query as a CTE in the downstream’s compiled SQL.

So fct_orders.sql says:

... from {{ ref('int_order_payments') }} p ...

And after dbt compile, target/compiled/dbt_project/models/marts/fct_orders.sql looks like:

with __dbt__cte__int_order_payments as (
    select
        order_id,
        sum(amount)              as total_amount,
        count(*)                 as payment_count
    from "main"."stg__payments"
    group by order_id
)
select ... from __dbt__cte__int_order_payments p ...

The aggregation runs inline, every time fct_orders is rebuilt. There’s no separate int_order_payments object to query, drop, or inspect.

When this is the right call

Ephemeral fits a narrow window:

  • Light intermediate logic. A handful of cases, a small grouping, a derived column. Not a full join chain.
  • Used by ≤ 2 downstream models. If three+ marts all ref() the same ephemeral, you’re recomputing the work 3× per dbt build. Materialize as a table.
  • Not queried directly. You can’t select * from int_order_payments if it’s ephemeral. Debugging means running the full compiled SQL of a downstream model.
  • No tests. unique / not_null need a real relation to query — they error against ephemeral models. (Singular tests work fine; they ref() the ephemeral and the SQL inlines.)

For our case (int_order_payments → only fct_orders consumes it, simple aggregation, no tests), ephemeral is fine. It’s not necessarily better than the table version you just built — for 99 rows the difference is invisible. But the exercise demonstrates the mechanism clearly.

The leftover-object gotcha

There’s a footgun specific to switching from table (or view) to ephemeral: the object dbt previously created stays in the warehouse. dbt doesn’t proactively drop it; it just stops touching it. So after the switch:

  • The manifest says int_order_payments is ephemeral
  • DuckDB still has the int_order_payments BASE TABLE from the previous exercise

To clean it, run dbt run --select +fct_orders --full-refresh. The + selector means “this model and everything upstream”; --full-refresh tells dbt to drop and recreate downstream tables. As a side effect, the leftover ephemeral object gets dropped too because dbt’s full-refresh logic notices it’s no longer materializable.

The exercise’s verifier is intentionally lenient about this — it doesn’t assert “the table doesn’t exist.” It asserts the manifest reports ephemeral and that fct_orders still has 99 rows. Those two together prove the inlining is working.

Common pitfalls

  • Adding generic tests to an ephemeral. dbt parses fine but errors at test time: “Cannot test an ephemeral model — there’s no relation to query.” Either remove the tests or change the materialization. The next exercise (incremental_basic) builds a fresh fact table that’s fine to test on.
  • Treating ephemeral as a free win. Each downstream re-runs the ephemeral’s query in its own compile. With three downstream models and a 5-second aggregation, that’s 15s on every dbt build instead of 5. The win is “fewer warehouse objects”; the cost is “duplicated work.”
  • Forgetting the leftover table. Until you --full-refresh, the old int_order_payments table sits in DuckDB and confuses anyone running ad-hoc queries against it. Always full-refresh after this kind of materialization downgrade.

Exercise walkthrough

Steps

1. Open dbt_project/models/intermediate/int_order_payments.sql. Change the config block’s value from table to ephemeral:

{{ config(materialized='ephemeral') }}

select
    order_id,
    sum(amount)              as total_amount,
    count(*)                 as payment_count
from {{ ref('stg__payments') }}
group by order_id

That’s the only edit — one word change. The select stays as-is.

2. Rebuild the marts chain with --full-refresh so the leftover int_order_payments table gets dropped and fct_orders is rebuilt with the inlined CTE:

cd dbt_project
dbt run --select +fct_orders --full-refresh

The + selector means “this model and everything upstream”; --full-refresh forces dbt to drop and recreate. The output should show int_order_payments skipped (it’s ephemeral, nothing to materialize) and fct_orders rebuilt as a table.

3. Confirm fct_orders still has 99 rows — proving the inlining works:

duckdb ../database/dev.duckdb -c "select count(*) from fct_orders"

Should print 99.

4. (Optional, for the visual win.) Look at the compiled fct_orders SQL and find the inlined CTE:

cat target/compiled/dbt_project/models/marts/fct_orders.sql | head -25

You’ll see a with __dbt__cte__int_order_payments as (...) block at the top — that’s the ephemeral’s query, inlined verbatim.

5. (Also optional but reinforcing.) Confirm int_order_payments is no longer a queryable table:

duckdb ../database/dev.duckdb -c "select * from int_order_payments limit 1"

Should error with “Catalog Error: Table with name int_order_payments does not exist!” — exactly the point of ephemeral.

6. Press v to verify.

What the verifier checks

  • dbt run --select +fct_orders exits 0.
  • target/manifest.json reports int_order_payments as materialized: ephemeral.
  • select count(*) from fct_orders returns 99 — proving the ephemeral inlining produced correct totals.

Common failure modes

Symptom Fix
Model 'int_order_payments' is materialized as 'table', expected 'ephemeral' The config block still says table. Change it to ephemeral.
Compilation Error: ephemeral model has tests attached If you added tests to int_order_payments somewhere (you didn’t in this stage, but worth knowing), generic tests on ephemerals are forbidden. Move the model to view or remove the tests.
fct_orders has 0 rows The full-refresh didn’t run, or fct_orders never got rebuilt against the new ephemeral. Re-run dbt run --select +fct_orders --full-refresh.
Catalog Error: Table with name int_order_payments does not exist! (when running queries against it directly) This is expected for an ephemeral — there’s no warehouse object. Verifier doesn’t assert the table doesn’t exist (since the leftover may persist), but the correct state is that the table is gone.
