Incremental models — load only the new rows

So far every model in this project gets fully rebuilt on every dbt run. For the 99-row jaffle_shop seed that’s instant. For a real event table — pageviews, transactions, orders — the source might be tens of millions of rows growing daily, and recomputing the entire transformation every time becomes the slowest step in your pipeline.

incremental is the materialization for that problem: first run loads the full history; subsequent runs load only the new rows.

The mechanism

An incremental model has three pieces:

  1. {{ config(materialized='incremental') }} — flag the materialization
  2. A regular select statement — what the model wants in its first-run “true” form
  3. An {% if is_incremental() %} filter — narrowing the select to “rows since last run”

The walkthrough below has the full file you’ll write. The shape is: a config() call at the top, a plain select from stg__orders, then a Jinja-wrapped where order_date > (select max(order_date) from {{ this }}) filter.

is_incremental() is a Jinja macro that returns true when all three of:

  • The target table already exists in the warehouse
  • The --full-refresh flag was not passed
  • The model is configured with materialized='incremental'

are true. On the first run, the table doesn’t exist yet, so is_incremental() is false and the filter is skipped — dbt does a create table ... as select <full query>. Every run after, the filter is included and dbt does an insert into ... select <filtered query>.

{{ this }} is a Jinja shortcut for the model’s own fully-qualified name. It’s how the filter says “go look at the existing table, find the watermark, and only load rows past it.” You can’t use {{ ref('this_model') }} recursively — this is the right form for self-reference.

Why both must be valid SQL

The block of code dbt runs is the entire file’s compiled output. So both branches of the is_incremental() if/else must produce valid SQL:

  • When is_incremental() is false, the file compiles to just the select (filter omitted).
  • When is_incremental() is true, the file compiles to the select with the filter.

If you put the where keyword inside the is_incremental() block but the filter outside, the false-branch compiles to select ... from foo where — broken SQL. Always put the entire where order_date > ... clause inside the {% if %} block.

What this exercise does

You’ll create models/marts/fct_order_events.sql from scratch — a pretty thin event-style fact (one row per order, with date and status), materialized incrementally. Run dbt build once to get the initial 99 rows. Run it again and watch dbt do a small insert of 0 rows because the source hasn’t grown.

The seed CSVs are static, so the second run is structurally meaningful but visually anti-climactic. To get a real demo of incremental adding new rows, you’d need a source that grows between runs — that’s what production data does naturally and what’s outside this course’s seed-based scope.

What dbt build does on the second run

$ dbt build --select fct_order_events
01:05 1 of 1 START sql incremental model main.fct_order_events
01:05 1 of 1 OK created incremental model main.fct_order_events ...

The word incremental in the log is the giveaway — same model name, different materialization handling. Behind the scenes:

-- Generated by dbt on the second run:
insert into "main"."fct_order_events"
select order_id, customer_id, order_date, status
from "main"."stg__orders"
where order_date > (select max(order_date) from "main"."fct_order_events")

Zero rows match the filter (the seed is static and max(order_date) already includes everything), so the insert is a no-op. The model still has 99 rows — it just got there via first run inserts all, second run inserts nothing.

Common pitfalls

  • is_incremental() typo (is_incremental without parens). Without the parens it’s a function reference, not a function call. Compiles, but the if-block always evaluates the function as truthy — so the filter is always included, including on the first run, which fails because {{ this }} doesn’t exist yet. Always include ().
  • Filter outside the {% if %} block. As noted: must wrap the entire where ... clause inside the if. The dangling where on first run breaks compile.
  • Self-referencing via ref() instead of {{ this }}. ref('fct_order_events') from inside fct_order_events.sql creates a circular dependency at parse time. {{ this }} is the special-case escape hatch for self-reference.
  • Forgetting --full-refresh after a structural change. If you add a new column or change a window in the SQL, the existing rows won’t have the new shape. dbt build --select fct_order_events --full-refresh drops and recreates the table from scratch, applying the new logic to the entire history.

Steps — exercise walkthrough

1. From the repo root, create the new model file:

touch dbt_project/models/marts/fct_order_events.sql

2. Paste this into fct_order_events.sql:

{{ config(materialized='incremental') }}

select
    order_id,
    customer_id,
    order_date,
    status
from {{ ref('stg__orders') }}

{% if is_incremental() %}
where order_date > (select max(order_date) from {{ this }})
{% endif %}

Key things:

  • {{ config(materialized='incremental') }} at the top.
  • {% if is_incremental() %} … {% endif %} wraps the entire where ... clause. The where keyword stays inside the block — without that, the first-run compile would emit a dangling where and fail.
  • {{ this }} is the model’s own fully-qualified relation. Don’t use {{ ref('fct_order_events') }} here — that creates a circular dependency.

3. First build — populates the table from scratch:

cd dbt_project
dbt build --select fct_order_events

The log says “START sql incremental model” and “OK created incremental model”. Behind the scenes dbt issued create table ... as select ... (the filter was skipped because is_incremental() returned false).

4. Confirm the table has 99 rows:

duckdb ../database/dev.duckdb -c "select count(*) from fct_order_events"

5. Second build — incremental insert path:

dbt build --select fct_order_events

The log still says “OK created incremental model” but this time dbt issued insert into ... select ... where order_date > .... The filter eliminated everything (no new rows in the seed), so the table is unchanged — still 99 rows.

6. Sanity check it stayed at 99:

duckdb ../database/dev.duckdb -c "select count(*) from fct_order_events"

7. Press v to verify.

What the verifier checks

  • dbt build --select fct_order_events exits 0 and every node succeeds.
  • target/manifest.json reports fct_order_events as materialized: incremental.
  • select count(*) from fct_order_events returns 99.

Common failure modes

Symptom Fix
Compilation Error: ... near "where" on the first run The where keyword is outside the {% if is_incremental() %} block. Move it inside — the entire clause should be wrapped.
Compilation Error: 'this' is undefined Typo on {{ this }} (extra space inside braces or capital This). Lowercase, exact name, double-curly braces.
Catalog Error: Table with name fct_order_events does not exist! on the second build The first build didn’t create the table. Re-run the first command and check the log for the OK created line.
Row count is 0 The first run hit is_incremental() returning true somehow (rare — usually a stale state where the table existed before). Try dbt build --select fct_order_events --full-refresh to force a clean rebuild.
Catalog Error: ... near "is_incremental" Spelling. The macro is is_incremental() exactly — including the parens. Without parens it’s a reference, not a call.
