Analysis-to-model — promoting one-off SQL to a tested mart

In Stage 3 you wrote analyses/top_customers_by_revenue.sql — a quick select ... group by ... limit 10 that compiles into target/compiled/ but doesn’t materialize. It’s the version of “ad-hoc SQL” that’s at least version-controlled and ref-aware.

Most analyses live and die that way: someone needs a number for a meeting, writes the query, gets the answer, moves on. But some analyses get queried again. And again. By dashboards. By other analysts. By external partners. At some point it crosses a threshold and becomes a production asset — and an analysis is the wrong shape for that.

That moment is when an analysis graduates to a model. This lesson is about doing that promotion well.

When does an analysis graduate?

Three signals, any of which is enough:

  1. It’s queried more than once. A one-off becomes an asset the second time someone needs the same number.
  2. A dashboard depends on it. Once Looker / Tableau / Metabase points at the SQL, the SQL has consumers, and consumers expect tests, schemas, and stable column names.
  3. It needs documentation or contracts. “What does lifetime_revenue mean?” is a question that gets asked. Models have descriptions; analyses don’t.

When any of these is true, the analysis stops being throwaway and starts being infrastructure. Promote it.

What changes between an analysis and a model?

Aspect Analysis Model
Location analyses/ models/marts/
Materialization None — compile-only Configurable (view, table, incremental, etc.)
Tests None Whatever you declare in YAML
Description None description: field
meta: / tags: No Yes — for ownership, PII flags, selection
Lineage One-off Part of the DAG; downstream models can ref() it
BI tools see it? No Yes (it’s a queryable table/view)

A promotion isn’t just a folder move. You’re declaring: “this SQL is now part of the analytics-engineering surface area. Here’s what it means, who owns it, and how I want it tested.”

The CTE refactor — imports → logic → final

When promoting, take the opportunity to clean up. The dbt community converged on a 3-section CTE pattern:

{{ config(materialized='table') }}

with

-- 1. IMPORT CTEs — one per upstream ref/source. Pure passthrough.
customers as (
    select * from {{ ref('dim_customers') }}
),

orders as (
    select * from {{ ref('fct_orders') }}
),

-- 2. LOGICAL CTEs — joins, aggregations, transformations
customer_revenue as (
    select
        c.customer_id,
        c.first_name,
        c.last_name,
        sum(o.amount) as lifetime_revenue,
        count(o.order_id) as lifetime_orders
    from customers c
    left join orders o on c.customer_id = o.customer_id
    group by c.customer_id, c.first_name, c.last_name
),

-- 3. FINAL CTE — the row shape that gets exposed
final as (
    select * from customer_revenue
    order by lifetime_revenue desc
)

select * from final

Why this shape:

  • Import CTEs at the top make every dependency visible at a glance. Reviewers can see what’s coming in without scanning the body.
  • Logical CTEs in the middle are where joins and transformations happen. Each CTE has a name that says what it computes.
  • A final CTE wraps the result so the bottom is always a one-liner. If you ever need to add post-processing (a filter, a column rename), it has an obvious place to go.

The pattern scales. A 5-line model uses one logical CTE; a 200-line model has fifteen. The shape is always the same.

YAML metadata — description, meta, tags

Once the model exists, declare it in _models.yml with rich metadata:

- name: mart_customer_revenue
  description: "Customer-grain lifetime revenue and order count, derived from fct_orders + dim_customers."
  config:
    meta:
      owner: data_eng
      pii: false
    tags:
      - revenue
      - finance
  columns:
    - name: customer_id
      description: "Stable customer identifier."
      tests:
        - unique
        - not_null
    - name: lifetime_revenue
      description: "Sum of fct_orders.amount across all orders for this customer."

The three knobs:

  • description: — human prose. Shows up in the dbt docs site, in BI tools that read dbt metadata, and in the manifest. Write it for the next person who’ll touch the model.
  • meta: — structured key/value pairs. Common keys: owner (who maintains it), pii (does this contain personal data?), team, business_critical, slack_channel. The schema is yours — dbt doesn’t enforce one — but every tool that reads the manifest can act on it.
  • tags: — flat string list. Used as a selection shortcut: dbt build --select tag:finance rebuilds every model tagged finance. Also useful for grouping in docs.

A model with no meta: or tags: is invisible to ownership tools. A model with both is governable: you can answer “who owns the revenue marts?” by querying the manifest.

Common pitfalls

  • Promoting too early. Not every analysis needs to be a model. Throwaway exploration belongs in analyses/ (or even outside the project). Promote when the query has recurring consumers, not just because the SQL feels important.
  • Skipping the CTE refactor. Copying the analysis SQL verbatim into models/marts/ and adding {{ config(materialized='table') }} works but loses the readability win. The 5-minute CTE refactor at promotion time is the cheapest cleanup you’ll ever do.
  • Forgetting meta: and tags:. A description alone is fine for a side project; in a real org, the model needs ownership metadata for incident routing and selection metadata for build orchestration. Add both at promotion time — retrofitting them later means trawling every model file.
  • Deleting the original analysis. Don’t. Keep analyses/top_customers_by_revenue.sql alongside the new mart. The analysis is the documentation: “this is what the model is meant to compute.” Some teams call this “audit artifacts” — files that show the lineage from idea to production.
