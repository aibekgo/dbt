Course complete

You started the course on Stage 0 reading about ETL vs ELT. You’re now at the bottom of Stage 7. In between, you built and tested every layer of a real dbt project. This is the recap.

What you can now do

Given a dbt project you’ve never seen, you can:

  • Read its config file (dbt_project.yml) and understand the materialization defaults.
  • Trace the lineage from raw sources to final marts using ref() / source().
  • Add a new staging model following naming conventions.
  • Add intermediate and mart models with proper CTE structure (imports → logic → final).
  • Write all four built-in tests (unique, not_null, accepted_values, relationships) plus singular tests in tests/ and custom generic tests in tests/generic/.
  • Switch a model’s materialization between view, table, ephemeral, and incremental — and explain when to pick each.
  • Configure incremental models with merge / delete+insert strategies and unique_key.
  • Snapshot a slowly-changing dimension with the check strategy and SCD2 metadata.
  • Write Jinja macros to deduplicate SQL across models.
  • Use packages — install via packages.yml, run dbt deps, call macros and tests from dbt_utils and dbt_expectations.
  • Run state-aware builds — dbt build --select state:modified+ --state ... to rebuild only what changed.
  • Declare exposures to make BI consumers visible in the lineage.
  • Tune test severity with severity: warn, where: row filters, and store_failures.
  • Use the dbt CLI fluently — parse, ls, show, compile, build, retry, clean.
  • Inspect target/ artifacts when something breaks: manifest.json, run_results.json, compiled/, run/.
  • Add a production target to profiles.yml and run dbt build --target prod.
  • Promote an analysis to a tested mart with meta:, tags:, descriptions, and column tests.

That’s the full surface area of dbt-core for a junior-to-mid analytics engineer. You’re equipped.

What this course did NOT cover

Be honest with yourself about the gaps so you know what to learn next on the job:

  • Real warehouse adapters. This course used DuckDB end-to-end. Snowflake, BigQuery, Databricks, Redshift, and Postgres each have adapter-specific quirks (data types, materialization options, performance characteristics). The dbt code you write is mostly portable; the configs are not.
  • dbt Cloud. The hosted offering with an IDE, scheduler, and built-in CI. If your team uses it, the basics (jobs, environments, CI integration) take a day to learn.
  • CI/CD setup. Knowing the patterns (1-trunk vs 2-trunk, state selection in CI) is half the battle. Wiring it up — GitHub Actions YAML, secrets management, artifact upload/download — is the other half. Pair with a senior engineer the first time.
  • dbt clone. Snowflake / BigQuery / Databricks have first-class table-cloning support that dbt exposes. Fast environment cloning is a real superpower; it’s not available on DuckDB so we skipped it.
  • dbt source freshness. Checks how stale your raw data is. Useful when you’re ingesting from real connectors with loaded_at_field timestamps; not demonstrable on static seeds.
  • The Semantic Layer + MetricFlow. Define metrics once, query them consistently across BI tools. Heavy setup, paid feature; mentioned in tooling_landscape.
  • Grants / row-level security. Each warehouse has different grant syntax; dbt has a grants: config that abstracts some of it. Warehouse-specific.
  • Performance tuning at scale. Partitioning, clustering, query optimization, model-level performance audits. Important once your project has 500+ models; out of scope here.
  • Multi-project / dbt Mesh. Splitting a monolithic project across teams with groups, access:, and contracts. Forward-looking topic.
  • dbt MCP, dbt Fusion + VS Code extension. AI-era tooling that’s reshaping how dbt code gets written. Mentioned in tooling_landscape; the setup is environment-specific.

None of these are scary topics. They’re just topics that require the right context (a real warehouse, a real CI pipeline, a real org structure) to learn well.

Where to go from here

Three paths, in increasing depth:

1. Use this on a real project (any size)

The fastest way to consolidate everything you just learned is to write dbt against a real warehouse. If you have access to a Postgres, Snowflake, or BigQuery instance at work — even a sandbox — clone this project, swap the adapter (type: duckdb → type: snowflake), and re-run it. You’ll hit your first adapter-specific issue within an hour, and you’ll learn a lot solving it.

If you don’t have a warehouse: start a BigQuery free tier account (10 GB free), or a Snowflake trial (30 days, $400 credit). Either is enough to build a real-feeling dbt project.

2. Read the dbt docs end-to-end

You’ve already encountered ~70% of what’s in the docs. The remaining 30% is the warehouse-specific configs, the deeper YAML reference, and the operational patterns. The docs are unusually well-written for technical documentation — readable in a weekend, valuable as a reference for years.

3. Contribute to a dbt package

Look at hub.getdbt.com. Pick a package that intrigues you (dbt_utils, dbt_expectations, audit_helper, dbt-coverage). Read the source. Find an issue tagged good first issue. Open a PR. This is the fastest way to graduate from user to practitioner — the day you’ve contributed code to the dbt ecosystem, the ecosystem starts to feel like yours.

A final note

dbt is a tool, and tools are mostly a question of muscle memory. You won’t write fluent dbt because you read about it; you’ll write fluent dbt because you’ve shipped fifty models and broken twenty of them. This course got you to model #50 in a controlled environment. Now go ship the next fifty in production.
