The Insurify data stack

Stage 0 has covered the ideas: ELT, the modern data team, cloud warehouses, dbt, and dbt flavors. This capstone shows how Insurify wires those ideas into a real production stack — so when Stage 1 has you scaffolding a dbt project, you know exactly which slot in the pipeline you’re filling.

The picture in one diagram

Sources — what flows in

Operational APIs

The transactional side of the business: leads coming in from the website, quote requests, bound policies, agent activity, claims events. Some come from internal services we own; some from third-party partners (carriers, comparison engines). Schemas vary, auth varies, and not every endpoint has a clean off-the-shelf connector — so this is the bucket where Custom Python earns its keep.

Marketing APIs

Ad-spend reporting, lifted straight from the platforms’ reporting APIs:

  • Google Ads — pulled via GAQL (the Google Ads Query Language).
  • Facebook (Meta) — pulled via the Graph API.
  • Microsoft Advertising — pulled via the Microsoft Advertising API.

These connectors are well-trodden and Airbyte handles them out of the box, so they take the direct path (skip S3, land straight in Redshift).

RDS tables

Operational data living in our managed Postgres / MySQL instances on Amazon RDS — application databases, internal tools, transactional state we want to analyze without hammering production. RDS replicates straight into Redshift (federated queries / AWS DMS / Redshift’s zero-ETL integration), so the rows arrive without going through S3 or Airbyte at all — the most direct path on the diagram.

Partner deliveries

Files, not APIs. Two flavors:

  • Drop into S3 — the partner has S3 write access (SFTP-to-S3, cross-account IAM role, a pre-signed URL, etc.). Files appear in a known prefix on a known cadence.
  • Email attachments — the partner emails files to a shared inbox. A small email processor watches that inbox, extracts attachments, validates them, and writes them into S3.

Either way, once the file is in S3 it joins the same downstream path as anything else in the lake.

Ingestion — six paths data takes to get to Redshift

Six recurring patterns. Pick the one that fits the source.

  1. API → Custom Python (DE team) → S3 → Airbyte → Redshift The default for non-standard sources. Custom Python handles the auth, pagination, retry, and any pre-landing transform; the raw extract lands in S3 (so we always have an archive); Airbyte then loads from S3 into Redshift on a schedule.

  2. API → Airbyte → Redshift (direct) When an off-the-shelf Airbyte connector exists and we don’t need an S3 archive, we skip the lake entirely. Most marketing sources (Google Ads, Facebook, Microsoft Advertising) take this path.

  3. RDS → Redshift (direct, no Airbyte) Operational Postgres / MySQL on RDS replicates straight into Redshift via federated queries, AWS DMS, or Redshift’s zero-ETL integration — no S3 landing, no Airbyte connector, no Custom Python step. Just the database showing up as queryable tables in the warehouse.

  4. S3 → Redshift via COPY For bulk file loads where Airbyte is overkill — backfills, large historical dumps, or sources where the file format already maps cleanly to a Redshift table. The Redshift COPY command parallel-loads from S3 in one shot.

  5. Partner → S3 directly The partner writes files into S3 (SFTP-to-S3, cross-account role). From there path 1 or path 3 picks them up — same as anything we put there ourselves.

  6. Partner → Email → email processor → S3 Files arrive as attachments to a shared inbox. The email processor pulls them out, drops them into S3, and from there path 1 or path 3 picks them up.

All of the above run on a daily incremental schedule by default. The unit of work is “yesterday’s slice” landed once a day, not streaming.

Storage — S3 as lake

S3 is the durable archive. Anything we ever pulled from an API or received from a partner gets a copy here, partitioned by date. If a transformation downstream goes wrong we can rebuild from S3 without re-extracting from the source. It’s also where files start their journey when partners drop them or the email processor unpacks them.

Warehouse + Transform — Redshift and dbt as one block

The diagram draws Redshift and dbt as a single block on purpose: dbt doesn’t run anywhere else. There is no separate transform engine, no Spark cluster, no pandas job — every dbt run compiles to SQL that executes inside Redshift. The compute that loaded the raw rows is the same compute that builds the curated marts.

What lives in that block:

  • Redshift holds two layers — raw schemas (what ingestion writes; roughly mirrors the source) and curated marts (what dbt produces; what consumers actually query).
  • dbt models read from raw and write back to marts, organized in the conventional stg → int → marts progression.
  • dbt CI/CD gates every change. Each PR triggers a Slim CI dbt build (compile + run + test); merging to main triggers a deploy. The same dbt build command underlies both — there is no separate deployment script to drift out of sync.

In ELT terms: the E and L end at Redshift’s raw schemas. The T is dbt, running inside the same warehouse.

Orchestration — Airflow on MWAA

That big purple arrow underneath the diagram is Airflow on MWAA (AWS Managed Workflows for Apache Airflow). It is the schedule that ticks the whole pipeline: ingestion jobs, the dbt runs that produce marts, freshness checks, data-quality alerts, and one-off operational tasks. dbt is the largest single tenant, but Airflow’s job is everything end-to-end — that’s why it’s drawn as one continuous arrow rather than another column.

Consumers — who reads the marts

Two distinct audiences, both reading from Redshift’s marts.

  • RTB ML model — real-time bidding. Marketing-spend, conversion, and policy data flowing out of Redshift feed the model that decides how much to bid for impressions in real time. Marts must be fresh and correct: the ML team is the most demanding internal consumer of the dbt project.
  • Mode and Hex — BI tools. Mode hosts dashboards and recurring reports for finance, marketing, and product. Hex is the notebook-style environment for ad-hoc analysis and prototyping. Both query Redshift directly; both rely on the marts dbt produces.

Where dbt sits, in one sentence

dbt is the T in this ELT — running on Redshift, fed by Custom Python + Airbyte + COPY + partner drops, orchestrated by Airflow on MWAA, gated by dbt’s own CI/CD, and consumed by the RTB ML model + Mode + Hex.
