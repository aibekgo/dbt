dbt_expectations — statistical assertions for richer data quality

dbt_utils (Stage 5) gives you DRY building blocks like generate_surrogate_key and expression_is_true. Useful, but those tests are still mostly about row-level shape: “this column is unique”, “this expression evaluates true”.

Real data quality often needs assertions about distributions: “the average order amount this week should be between $10 and $200”, “95% of rows should have a non-null email”, “this column’s values should fall within ±2 standard deviations of the historical mean”. Those need a test framework with statistical primitives.

That’s dbt_expectations. It’s a port of the popular Great Expectations Python library to dbt — same idea, dbt-native.

What’s in the package

dbt_expectations ships ~50 generic tests, organized into a few families:

Family Examples
Value-range tests expect_column_values_to_be_between, expect_column_values_to_match_regex, expect_column_values_to_be_in_set
Aggregate tests expect_column_mean_to_be_between, expect_column_median_to_be_between, expect_column_max_to_be_between
Distribution tests expect_column_values_to_be_within_n_moving_stdevs, expect_column_quantile_values_to_be_between
Row-shape tests expect_table_row_count_to_be_between, expect_compound_columns_to_be_unique
Cross-column tests expect_column_pair_values_A_to_be_greater_than_B
Pattern tests expect_column_values_to_match_regex_list, expect_column_values_to_be_increasing

The full list is on the package’s GitHub README — much richer than what fits in a lesson.

How to install

Same pattern as dbt_utils:

  1. Add the package to packages.yml.
  2. Run dbt deps to clone it into dbt_packages/dbt_expectations/.
  3. Reference its tests with the dbt_expectations. prefix.
# dbt_project/packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
  - package: calogica/dbt_expectations
    version: [">=0.10.0", "<0.11.0"]

The version range tracks the package’s semver. 0.10.x is current as of this course; check the GitHub releases page if you want to bump.

What expect_column_values_to_be_between does

The Stage 6 exercise uses this one specifically. It asserts that every value in a column falls within a [min_value, max_value] range:

- name: amount
  tests:
    - dbt_expectations.expect_column_values_to_be_between:
        min_value: 0
        max_value: 100

Compiles to roughly:

select *
from "main"."fct_orders"
where amount < 0 or amount > 100

Returns 0 rows when every amount is in [0, 100]. Returns the violators otherwise.

Optional knobs:

  • row_condition — filter to a subset of rows (similar to where: for built-in tests)
  • strictly — true for < / > (strict bounds), false for <= / >= (default — inclusive)
  • group_by — apply the assertion per group (e.g., per customer_id)

When to reach for it vs dbt_utils.expression_is_true

dbt_utils.expression_is_true is the catch-all: any boolean SQL expression you can write. It works for ranges:

tests:
  - dbt_utils.expression_is_true:
      expression: "amount >= 0 and amount <= 100"

That’s equivalent to expect_column_values_to_be_between. Same result, different syntax.

When to pick which:

  • dbt_expectations when there’s a named test for your assertion. The name is self-documenting (expect_column_mean_to_be_between reads better than expression_is_true(expression='avg(amount) between 1 and 500')).
  • dbt_utils.expression_is_true when the assertion doesn’t have a named test, or when the SQL is simple enough that naming is overkill.

For most real projects, dbt_expectations is the better default for non-trivial assertions because the named tests are clearer in PRs and in the docs site.

Where Stage 6’s exercise applies it

We add expect_column_values_to_be_between on fct_orders.amount with min_value: 0, max_value: 100. Why those bounds?

  • The seed converts cents to dollars in stg__payments, so amounts are dollar values.
  • The seed has zero negatives (refunds aside, none in raw data).
  • The largest total_amount per order is well under $100.

So the test passes on the seed. In a real project, the bounds would come from business knowledge: “a single order should never exceed $1000” or “a payment under $0.50 is suspicious”.

Common pitfalls

  • Wrong package name in packages.yml. It’s calogica/dbt_expectations (the org is calogica). Old references to dbt-labs/dbt_expectations are wrong — dbt Labs doesn’t maintain it.
  • Forgetting dbt deps after editing packages.yml. Same as Stage 5: editing the YAML alone doesn’t install. Always run dbt deps.
  • Calling without the prefix. {{ expect_column_values_to_be_between }} (no prefix) silently looks up a local macro and fails. Always dbt_expectations.expect_column_values_to_be_between.
  • Bounds that are actually wrong for your data. expect_column_values_to_be_between(min_value: 0, max_value: 1) on a column with values up to 100 will fail the test — but the test isn’t wrong; your bounds are. Check the data first; pick bounds that match your business expectations.

Exercise walkthrough

Steps

1. Open dbt_project/packages.yml. Add the new package as a second entry. The full file should read:

packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
  - package: calogica/dbt_expectations
    version: [">=0.10.0", "<0.11.0"]

Note: the org is calogica, not dbt-labs.

2. Install the new package:

cd dbt_project
dbt deps

You should see two packages installed (or “up to date” for dbt_utils, “installed” for dbt_expectations). After this, dbt_packages/dbt_expectations/ exists.

3. Open dbt_project/models/marts/_models.yml. Find the fct_orders block. Replace it with this version that adds an amount column entry with the new test:

version: 2

models:
  - name: fct_orders
    description: "One row per order, denormalized with customer attributes and payment totals."
    columns:
      - name: order_id
        description: "Primary key. Inherited from stg__orders."
        tests:
          - unique
          - not_null
      - name: customer_id
        description: "Foreign key to dim_customers."
        tests:
          - not_null
          - relationships:
              to: ref('dim_customers')
              field: customer_id
      - name: amount
        description: "Total dollar amount paid across all payments for this order."
        tests:
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 0
              max_value: 100

The new column entry has dbt_expectations.expect_column_values_to_be_between as its test, with min_value and max_value arguments.

4. Run the tests:

dbt test --select fct_orders

You should see all four tests pass: unique, not_null, relationships, and the new expect_column_values_to_be_between.

Done. PASS=4 WARN=0 ERROR=0 SKIP=0 TOTAL=4

5. Confirm the new test count in the manifest:

dbt ls --resource-type test --select fct_orders

Four lines, including one starting with dbt_expectations_expect_column_values_to_be_between_fct_orders_amount.

6. Press v to verify.

What the verifier checks

  • dbt_project/dbt_packages/dbt_expectations/ exists (proves dbt deps ran successfully).
  • dbt test --select fct_orders exits 0 with all tests passing.
  • target/manifest.json shows fct_orders has at least 4 tests.

Common failure modes

Symptom Fix
path 'dbt_project/dbt_packages/dbt_expectations' does not exist You skipped dbt deps. Run it from inside dbt_project/.
Encountered an error: package_name 'dbt-labs/dbt_expectations' not found The package is published under calogica/dbt_expectations, not dbt-labs/. Fix the org prefix.
Compilation Error: macro 'expect_column_values_to_be_between' is undefined You forgot the dbt_expectations. prefix. Tests in packages need the package name as a prefix.
Test reports FAIL The data violates the bounds. Run select max(amount), min(amount) from fct_orders to see the actual range — adjust min_value / max_value if needed. With the seed data, max should be under $100 and min should be 0.
Model 'fct_orders' has 3 test(s) — expected at least 4 The new test didn’t attach. Check the YAML indent — dbt_expectations.expect_column_values_to_be_between: is under tests: -, with min_value: and max_value: nested under that.
