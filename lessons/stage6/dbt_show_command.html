dbt show — preview model output without rebuilding

You’ll write hundreds of dbt models over your career. Most of them you want to test before you commit:

  • “Did my new column come out right?”
  • “How does this group by change the row count?”
  • “What’s the actual data look like for that one customer who’s been weird?”

The naive workflow: dbt run --select my_model, then duckdb dev.duckdb -c "select * from my_model limit 5". Two commands, one swaps tools mid-flow. dbt show does it in one — and does it without re-materializing.

What dbt show actually does

dbt show --select <model> runs the model’s compiled SQL as a query, returns the first N rows, and prints them in a nicely formatted table. It does not create or update a warehouse object — no create table, no insert, no merge. Pure read.

dbt show --select fct_orders --limit 5

Output (truncated):

Previewing node 'fct_orders':
| order_id | customer_id | first_name | last_name | order_date | status    | amount | payment_count |
| -------- | ----------- | ---------- | --------- | ---------- | --------- | ------ | ------------- |
|     1    |     1       | Michael    | Perkins   | 2018-01-01 | returned  |  10.00 |       1       |
|     2    |     3       | Shawn      | Mccoy     | 2018-01-02 | completed |  20.00 |       2       |
|     ...  |     ...     |     ...    |     ...   |     ...    |    ...    |   ...  |      ...      |

The --limit defaults to 5; bump it for more rows. dbt’s table renderer handles wide schemas reasonably well, though for very wide output you’ll want to scope columns with a custom inline query (see below).

Two modes

dbt show has two invocation patterns:

1. Preview an existing model

The most common use:

dbt show --select fct_orders --limit 10

dbt looks up fct_orders in the manifest, compiles its SQL with all the ref() and macro substitutions, runs it, returns rows. The model in the warehouse may or may not be up to date — show doesn’t care. It runs the current compiled SQL fresh.

2. Preview an inline SQL query

Less common but useful for ad-hoc checks:

dbt show --inline "select status, count(*) from {{ ref('fct_orders') }} group by 1"

The --inline flag tells dbt to compile and run the given Jinja-SQL expression directly, with full access to ref(), source(), macros, etc. It’s like a one-off analysis without writing a file. Especially useful for “what does this aggregation look like” type checks during development.

Why this beats select * from foo in a SQL client

You could fire up duckdb dev.duckdb and select * from fct_orders limit 5. That works, but it has three weaknesses compared to dbt show:

Weakness of raw SQL What dbt show fixes
Tied to whatever’s currently in the warehouse — even if the model file changed since the last dbt run, the SQL client sees the stale table Compiles the current model file, so you see what the next dbt run would produce
Doesn’t resolve ref() / source() / macros — you have to type fully-qualified table names Full Jinja resolution, just like dbt run
Lives outside the dbt log stream, so it’s not captured in target/run_results.json Output is part of the standard dbt log

For ephemeral models (Stage 4), dbt show is the only way to preview the data — there’s no warehouse object to query directly. dbt compiles the model’s CTE chain and runs it inline.

When NOT to use dbt show

  • For data you intend to materialize anyway. Just run the model. dbt show reads-only; dbt run reads + writes. If you’re going to ship the change, run it.
  • For pipelines that need warehouse persistence. dbt show doesn’t change the warehouse; the table you might be testing against in BI doesn’t exist after dbt show.
  • For massive models. dbt show runs the full SQL; --limit only caps the output. A model that aggregates 100M rows will still take a minute to run, even if you only want 5 rows back. For exploration on big data, materialize as a view first, then preview.

Common pitfalls

  • Forgetting --limit. Default is 5, but if you accidentally pass --limit 100000 on a wide table, the output drowns the terminal. --limit 20 is a reasonable interactive default.
  • Treating show like run. dbt show doesn’t update the warehouse. If you inspect a model with dbt show, see good output, then expect the BI tool to reflect it — you’ll be confused. Run the model after.
  • Using dbt show for tests. It just prints rows; it doesn’t validate them. Use dbt test for assertions.

The exercise: run dbt show --select fct_orders --limit 5, see the output, press v. Tiny exercise; the value is the muscle memory.
