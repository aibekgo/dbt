severity: warn and where: — soft tests with row-level filters

The accepted_values test on stg__orders.status from Stage 3 is hard-pinned: a value outside [placed, shipped, completed, return_pending, returned] fails the test, fails the run, and blocks downstream models. That’s the right behavior most of the time. But not always.

This exercise covers two test config knobs that let you ship tests with softer behavior: severity (downgrade error to warn) and where (scope the test to a row subset).

What severity: warn does

By default, every test has severity: error. When the test query returns ≥1 bad row, dbt:

  1. Marks the test as failed
  2. Marks the run as failed (exits non-zero)
  3. Skips downstream models that depend on this test’s model in dbt build

severity: warn softens that to:

  1. Marks the test as warned
  2. Run continues, exits 0 successfully
  3. Downstream models still build

The warning shows up in the dbt logs as [WARN]-tagged output and in target/run_results.json with status: "warn". CI systems that only check the exit code see green; humans reading the logs see the issue.

When to reach for it:

  • Informational tests. A expect_column_values_to_be_between on a metric that varies — a warning when last week’s value is outside the historical range, but you don’t want to block deployment because of natural fluctuation.
  • Tests on data you don’t fully own. A not_null on a third-party feed where occasional gaps happen — you want visibility, not a blocked deploy.
  • Migration windows. Temporarily downgrade strict tests during a migration when you know edge cases are coming, then revert.

When NOT to reach for it:

  • Primary key uniqueness — should always hard-fail
  • Foreign key integrity — same
  • Anything where bad data would silently break business logic downstream

What where: does

where: is a row-level filter applied to the test query. dbt wraps your test SQL in something like:

select count(*) from (
    select * from <test_query>
    where <your where clause>
) bad_rows

(Conceptually — the actual SQL varies by test type.) The test only counts violations among rows matching the where.

- name: status
  tests:
    - accepted_values:
        values: [placed, shipped, completed, return_pending, returned]
        config:
          where: "order_date >= '2018-01-01'"

This says: “Only check the assertion on orders from 2018 onward.” Older orders with legitimately weird statuses (a legacy pending value before the migration) won’t trigger the test.

Use cases:

  • Time-bound assertions. “Status enum is enforced only on recent orders” — legacy data stays untouched.
  • Subset-specific rules. “Email must not be null only for active customers” — disabled accounts can have null emails.
  • Excluding known issues. “Foreign key integrity except for these 5 rows we’ve already triaged” — a temporary workaround while you fix the underlying issue.

The risk: where: is the easiest way to make a failing test pass by filtering away the failures. Always document why the where clause exists in a comment alongside the YAML. Future-you will thank you.

Combined: severity: warn + where:

The two compose naturally. The test in this exercise:

- name: status
  description: "Order lifecycle state."
  tests:
    - accepted_values:
        values: [placed, shipped, completed, return_pending, returned]
        config:
          severity: warn
          where: "order_date >= '2018-01-01'"

Reads as: “Among orders from 2018 onward, warn (don’t error) if any row’s status isn’t in the canonical set.” Both knobs at once — soft + scoped.

For our seed data, every order’s status IS in the canonical set, so the test passes with no warnings either way. The exercise demonstrates the syntax; the runtime behavior on this dataset is silent success.

How dbt records the config in the manifest

After dbt parse, the test’s manifest entry includes:

{
    "test_metadata": {
        "name": "accepted_values",
        ...
    },
    "config": {
        "severity": "warn",
        "where": "order_date >= '2018-01-01'",
        ...
    }
}

The verifier doesn’t parse the manifest config directly — it just checks the YAML file contains the string severity: warn. That’s looser than checking the manifest, but it’s simpler and catches the same learner mistakes (forgetting to add the config, putting it under the wrong key).

Common pitfalls

  • Putting severity: outside the config: block. It must be nested under config:. Loose severity: warn directly under the test name doesn’t take effect.
  • where: clauses with unquoted column names. dbt wraps your where in SQL, so column names need to be valid identifiers in the warehouse. For DuckDB, lowercase column names work without quotes.
  • Testing severity: warn with no actual failures. It’s hard to see the difference between error and warn if the test is passing. To verify the config is working, temporarily change one of the values: entries to break the test — the run should warn instead of erroring. Revert before pressing v.
