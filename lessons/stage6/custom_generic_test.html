Custom generic tests — codify a project convention as a reusable test

You’ve used three flavors of test so far:

  • Built-in generic tests — unique, not_null, accepted_values, relationships (Stage 3). Predefined, reused everywhere.
  • Singular tests — handwritten SQL files in tests/. One model, one assertion, no parameters (Stage 3).
  • Package tests — dbt_utils.expression_is_true, soon dbt_expectations.expect_column_values_to_be_between (Stage 5/6). Defined elsewhere, called by name.

There’s a fourth: custom generic tests. You write the test logic once, parameterize it on model and column_name, and apply it to as many model+column pairs as you like. They sit halfway between singular tests (project-specific) and built-ins (reusable).

What a custom generic test looks like

A custom generic test lives in dbt_project/tests/generic/<name>.sql. The walkthrough below has the full file you’ll write — a {% test non_negative(model, column_name) %} block whose body is just select * from {{ model }} where {{ column_name }} < 0. Three things to flag about the shape:

  • {% test name(args) %} — same shape as {% macro %}, just a different keyword. The first two args are always model (the parent dbt relation) and column_name (the column being tested). You can add more args for parameterized tests.
  • The body is a select returning the bad rows — same contract as a singular test. 0 rows → pass; ≥1 rows → fail.
  • {{ model }} and {{ column_name }} — Jinja substitutes these at parse time with the actual model relation and column name from the YAML call site.

How to apply it

In any schema YAML, list the test under a column’s tests: block — without the dbt_utils. or dbt_expectations. prefix, because it’s a project-local test:

columns:
  - name: total_amount
    tests:
      - non_negative
  - name: payment_count
    tests:
      - non_negative

Two columns, one test, both pass through the same non_negative macro. dbt expands each into its own test node in the manifest:

  • test.dbt_project.non_negative_int_order_payments_total_amount
  • test.dbt_project.non_negative_int_order_payments_payment_count

The naming pattern is <test_name>_<model>_<column> — same as the built-ins (unique_stg__customers_customer_id, etc.).

When to write one

Use this decision tree:

  1. Does a built-in cover the assertion? Use the built-in.
  2. Does dbt_utils or dbt_expectations cover it? Use the package.
  3. Is the assertion specific to one model only? Write a singular test in tests/.
  4. Is the assertion a project-wide convention (e.g., “every revenue column should be non-negative”) applied across multiple models? Write a custom generic test.

The Stage 3 singular test (assert_no_negative_payment_totals.sql) was a one-shot — only int_order_payments.total_amount got that check. Promoting it to a custom generic test (non_negative) lets you apply the same check to any numeric column without copy-pasting the SQL.

Where the file lives — tests/generic/ vs tests/

Folder What lives there How dbt finds it
tests/ Singular test SQL files (a select returning bad rows). dbt scans every .sql under tests/ and treats each file as a test node. Files in subfolders work too — but conventionally, only the root level holds singular tests.
tests/generic/ Custom generic test definitions ({% test name(...) %} blocks). dbt scans tests/generic/ for files containing test blocks and registers each one as a callable generic test.

The default dbt init scaffold doesn’t create tests/generic/ — you’ll create it for this exercise.

Why “generic”?

The test is generic because it can be called against any column. The built-ins (unique, not_null) are generic by default — they take a column and check a property. Yours follows the same pattern.

The alternative — singular — is “specific” to one place. Less reusable, but quicker to write for one-off assertions.

Common pitfalls

  • Putting the file at tests/non_negative.sql instead of tests/generic/non_negative.sql. dbt would scan it as a singular test (which expects raw select SQL, not a {% test %} block) and error out. The folder structure matters.
  • Forgetting {% endtest %}. Like {% macro %} ↔ {% endmacro %}, you need an explicit closer.
  • Naming collisions with built-ins. {% test unique(model, column_name) %} would override dbt’s built-in unique test across the whole project. Sometimes that’s intentional (a custom variant); usually it’s a bug. Pick names that don’t shadow built-ins unless you mean to.
  • Hard-coding the column. {% test non_negative(model) %} (no column_name parameter) makes the test apply to a “model-level” check. That’s valid for some tests but limits reuse — best to keep column_name as a parameter.

Exercise walkthrough

Steps

1. Open dbt_project/models/intermediate/int_order_payments.sql and remove the {{ config(materialized='ephemeral') }} line — leaving just the select. Without an explicit override, it falls back to the dbt default for the folder, which is view.

The file should now read:

select
    order_id,
    sum(amount)              as total_amount,
    count(*)                 as payment_count
from {{ ref('stg__payments') }}
group by order_id

Re-run it so the warehouse rebuilds it as a view:

cd dbt_project
dbt run --select int_order_payments

2. From the repo root, create the tests/generic/ folder and the test file:

mkdir -p dbt_project/tests/generic
touch dbt_project/tests/generic/non_negative.sql

3. Paste this into non_negative.sql:

{% test non_negative(model, column_name) %}

select *
from {{ model }}
where {{ column_name }} < 0

{% endtest %}

The structure: - {% test non_negative(model, column_name) %} opens the test definition. - The body is a select returning the bad rows — values where the assertion fails (i.e., < 0). - {% endtest %} closes the block.

(Note: < 0 not <= 0 — zero is a legitimate value for a refunded order with total_amount = 0.)

4. Create dbt_project/models/intermediate/_models.yml (this folder didn’t have a schema YAML before):

version: 2

models:
  - name: int_order_payments
    description: "Per-order rollup of payment events from stg__payments."
    columns:
      - name: order_id
        description: "Primary key."
        tests:
          - unique
          - not_null
      - name: total_amount
        description: "Sum of all payment amounts (in dollars) for the order. Refunds can sum to 0."
        tests:
          - non_negative
      - name: payment_count
        description: "Number of payment events that rolled up into this order."
        tests:
          - non_negative

Three tests on int_order_payments: unique+not_null on order_id, plus the new non_negative test on both numeric columns.

5. Run the tests:

dbt test --select int_order_payments

You should see four tests run and pass:

Done. PASS=4 WARN=0 ERROR=0 SKIP=0 TOTAL=4

(unique, not_null, plus two non_negative calls.)

6. Confirm the new tests show up in the manifest:

dbt ls --resource-type test --select int_order_payments

You should see lines like:

dbt_project.unique_int_order_payments_order_id
dbt_project.not_null_int_order_payments_order_id
dbt_project.non_negative_int_order_payments_total_amount
dbt_project.non_negative_int_order_payments_payment_count

The naming pattern matches the built-ins.

7. Press v to verify.

What the verifier checks

  • dbt_project/tests/generic/non_negative.sql exists.
  • The file contains the literal string {% test non_negative.
  • dbt test --select int_order_payments exits 0 with all tests passing.

Common failure modes

Symptom Fix
path 'dbt_project/tests/generic/non_negative.sql' does not exist The file is in the wrong folder. It must be under tests/generic/, not tests/.
Compilation Error: 'non_negative' is undefined Two possibilities: (a) the file is in tests/ instead of tests/generic/ — dbt parses singular tests differently; (b) the {% test ... %} block has a syntax error and didn’t register. Run dbt parse to see the exact error.
dbt test errors with “compiled SQL is not a valid select” The body of the test isn’t a select statement. The body must be a query returning rows; nothing else.
Compilation Error: macro 'non_negative' is undefined (in YAML) Means dbt couldn’t find the test. Check the file path again, and confirm dbt parse succeeds.
Test reports FAIL The data violates the assertion. Run select * from int_order_payments where total_amount <= 0 to see what’s actually there — shouldn’t happen on the seed data, but if it does, the test is doing its job.
