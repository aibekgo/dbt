Splitting one source into many

In Stage 1 you declared one source — raw — that owns all three tables: customers, orders, payments. That works, but it’s a fiction. In a real warehouse those tables don’t come from one place. Customers and orders come out of the application database; payments come from Stripe. They have different owners, different update cadences, different schemas, and different things that go wrong with them.

This exercise refactors the single raw source into two sources that match the real systems: jaffle_shop (the app) and stripe (the payment processor).

Why split?

A source in dbt is the place where you describe one upstream system. Splitting them gives you four practical wins:

Win What it looks like
Lineage that explains itself The DAG shows two green source nodes. Anyone reading the docs site can see at a glance that fct_orders depends on the app and on Stripe — not on some opaque “raw” blob.
Per-system freshness rules Stripe’s payments may sync every 15 min; the app’s tables sync nightly. dbt source freshness lets you set different warn_after / error_after thresholds per source — impossible if they’re all bundled.
Per-system ownership When a column drops out, you know which team to ping (the Stripe integration team vs the app team). Owner metadata can live on the source block.
Selectors that match the team mental model dbt run --select source:stripe+ rebuilds everything downstream of payments — useful when Stripe schema changes — without touching app-side models.

The cost is one extra YAML block. Always worth it once you have more than one upstream system.

What changes in _sources.yml

Stage 1 left you with one source block named raw that owned all three tables. The walkthrough below has the full replacement YAML — two top-level source blocks, with raw_customers and raw_orders moving under jaffle_shop and raw_payments moving under stripe.

The schema: main field stays the same in both because, in this course, scripts/ingest_raw.py happens to land all three CSVs in DuckDB’s main schema. In a real warehouse the two sources would usually live in different schemas (e.g. raw.app_db vs raw.stripe), and you’d reflect that here.

The source() call has to follow

Once you rename the source block, the model that referenced the old name stops compiling — the macro can’t find a source called raw. The walkthrough’s Step 2 shows the matching update to stg__customers.sql (just swap the first argument of source(...) from 'raw' to 'jaffle_shop'). If you forget this edit, dbt run --select stg__customers fails with a “Found a source… but no matching source declaration” error — the verifier surfaces it.

What you can do once it’s done

The selector dbt ls --select source:stripe+ will return only the payments-side downstream models — useful in the next exercise when you start building stg__payments. (The walkthrough’s Step 4 shows dbt ls --resource-type source listing the two new groups.)

Common pitfalls

  • Forgetting to update the source() call in stg__customers.sql. The YAML edit alone leaves the model broken — the macro looks up source raw, doesn’t find it, and the run fails. Update both files together.
  • Putting schema: at the top level instead of per-source. Each source block needs its own schema: field. They happen to be the same value here (main), but that’s a coincidence — usually they’d differ.
  • Re-using the same source name twice. YAML lets you, dbt doesn’t — you’ll get a “duplicate source name” error on dbt parse. Each name: must be unique within the project.

Exercise walkthrough

Steps

1. From the repo root, open dbt_project/models/staging/_sources.yml and replace its contents with:

version: 2

sources:
  - name: jaffle_shop
    description: "Application data from the Jaffle Shop app database"
    schema: main
    tables:
      - name: raw_customers
      - name: raw_orders

  - name: stripe
    description: "Payment data landed from the Stripe payment processor"
    schema: main
    tables:
      - name: raw_payments

Notice what changed: two top-level source blocks, customers + orders under jaffle_shop, payments under stripe. The schema: field stays as main because that’s where scripts/ingest_raw.py lands the CSVs.

2. Open dbt_project/models/staging/stg__customers.sql. Update the from line so it references the new source:

select
    id          as customer_id,
    first_name,
    last_name
from {{ source('jaffle_shop', 'raw_customers') }}

The first argument of source() must match the name: field of the source block. Keep everything else the same.

3. Sanity-check the project parses and runs:

cd dbt_project
dbt run --select stg__customers

You should see the same green success message as in Stage 1. The compiled SQL still resolves to main.raw_customers — only dbt’s understanding of where that table came from has changed.

4. List the new sources to confirm both are on the DAG:

dbt ls --resource-type source

Three lines, grouped by source:

dbt_project.jaffle_shop.raw_customers
dbt_project.jaffle_shop.raw_orders
dbt_project.stripe.raw_payments

5. Press v to verify.

What the verifier checks

  • Source jaffle_shop is declared in target/manifest.json with both raw_customers and raw_orders.
  • Source stripe is declared with raw_payments.
  • dbt run --select stg__customers still exits 0 — proving the SQL edit kept the model parseable.

Common failure modes

Symptom Fix
Found a source named 'raw' but there is no matching source declaration You updated the YAML but forgot the SQL — stg__customers.sql still references source('raw', ...). Change the first argument to 'jaffle_shop'.
Source 'jaffle_shop' not found in target/manifest.json The YAML edit didn’t land — confirm the file was saved at dbt_project/models/staging/_sources.yml and the top-level key is sources: (plural).
Compilation Error: duplicate source name 'jaffle_shop' You have two - name: jaffle_shop blocks. Each name: must be unique.
YAML parse error Indentation. YAML uses spaces (two per level), never tabs.
