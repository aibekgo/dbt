Splitting one source into many

In Stage 1 you declared one source — raw — that owns all three tables: customers, orders, payments. That works, but it’s a fiction. In a real warehouse those tables don’t come from one place. Customers and orders come out of the application database; payments come from Stripe. They have different owners, different update cadences, different schemas, and different things that go wrong with them.

This exercise refactors the single raw source into two sources that match the real systems: jaffle_shop (the app) and stripe (the payment processor).

Why split?

A source in dbt is the place where you describe one upstream system. Splitting them gives you four practical wins:

Win What it looks like
Lineage that explains itself The DAG shows two green source nodes. Anyone reading the docs site can see at a glance that fct_orders depends on the app and on Stripe — not on some opaque “raw” blob.
Per-system freshness rules Stripe’s payments may sync every 15 min; the app’s tables sync nightly. dbt source freshness lets you set different warn_after / error_after thresholds per source — impossible if they’re all bundled.
Per-system ownership When a column drops out, you know which team to ping (the Stripe integration team vs the app team). Owner metadata can live on the source block.
Selectors that match the team mental model dbt run --select source:stripe+ rebuilds everything downstream of payments — useful when Stripe schema changes — without touching app-side models.

The cost is one extra YAML block. Always worth it once you have more than one upstream system.

Today’s _sources.yml — single source

This is what Stage 1 left behind:

version: 2

sources:
  - name: raw
    description: "Jaffle shop raw tables landed by scripts/ingest_raw.py"
    schema: main
    tables:
      - name: raw_customers
      - name: raw_orders
      - name: raw_payments

One source named raw, three tables under it. From SQL you reference them as {{ source('raw', 'raw_customers') }}.

After the split

You’ll change the file to declare two sources:

version: 2

sources:
  - name: jaffle_shop
    description: "Application data from the Jaffle Shop app database"
    schema: main
    tables:
      - name: raw_customers
      - name: raw_orders

  - name: stripe
    description: "Payment data landed from the Stripe payment processor"
    schema: main
    tables:
      - name: raw_payments

Three things change:

  1. Two top-level entries under sources: instead of one.
  2. raw_customers and raw_orders move under jaffle_shop, since the app emits both.
  3. raw_payments moves under stripe — payments come from a different system entirely.

The schema: main field stays the same in both because, in this course, scripts/ingest_raw.py happens to land all three CSVs in DuckDB’s main schema. In a real warehouse the two sources would usually live in different schemas (e.g. raw.app_db vs raw.stripe), and you’d reflect that here.

The source() call has to follow

stg__customers.sql references the old source by name:

from {{ source('raw', 'raw_customers') }}

Once you delete the raw source declaration, that line stops compiling — the macro can’t find a source called raw. Update it to:

from {{ source('jaffle_shop', 'raw_customers') }}

The first argument always matches the source’s name: field. If you forget this edit, dbt run --select stg__customers fails with a “Found a source… but no matching source declaration” error — the verifier surfaces this.

What you can do once it’s done

dbt ls --resource-type source

Should now print two groups:

dbt_project.jaffle_shop.raw_customers
dbt_project.jaffle_shop.raw_orders
dbt_project.stripe.raw_payments

And selectors like dbt ls --select source:stripe+ will return only the payments-side downstream models — useful in the next exercise when you start building stg__payments.

Common pitfalls

  • Forgetting to update the source() call in stg__customers.sql. The YAML edit alone leaves the model broken — the macro looks up source raw, doesn’t find it, and the run fails. Update both files together.
  • Putting schema: at the top level instead of per-source. Each source block needs its own schema: field. They happen to be the same value here (main), but that’s a coincidence — usually they’d differ.
  • Re-using the same source name twice. YAML lets you, dbt doesn’t — you’ll get a “duplicate source name” error on dbt parse. Each name: must be unique within the project.
