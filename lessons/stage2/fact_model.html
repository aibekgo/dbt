The fact table — what an analyst actually queries

Three staging models, one intermediate. None of them is what someone would open BI on. The fact is the model an analyst runs select * from against and gets answers — joins resolved, columns named for humans, grain set deliberately.

This exercise builds fct_orders: one row per order, every column the analyst needs to answer “who ordered what, when, for how much.”

Fact vs dimension

The data warehouse vocabulary:

  • Facts are events — orders, sessions, transactions, page views. The grain is “one event per row.” fct_orders has one row per order. fct_payments would have one row per payment. The columns are mostly numeric measures (amounts, counts, durations) with foreign keys out to dimensions.
  • Dimensions are things — customers, products, locations. The grain is “one thing per row.” dim_customers has one row per customer. The columns are mostly attributes (names, tiers, regions).

Stage 1 already built one dimension (dim_customers). This exercise adds the corresponding fact, and the two together are what most analyses join.

Set the grain first

The hardest part of writing a fact isn’t the SQL — it’s deciding the grain. “One row per what?” Pick wrong and the row count lies (joins fan out, aggregates double-count, foreign keys aren’t actually unique).

Here, the grain is one row per order. That means:

  • stg__orders is the driving table — its row count sets the row count of the fact.
  • Everything else gets left join-ed in. Joins must not multiply rows. Customers join 1:1 (a customer per order). Payments join via int_order_payments, which we already collapsed to one-row-per-order — so the join is also 1:1.
  • If you joined directly to stg__payments (113 rows), you’d get 113 rows out. That’s why the intermediate exists.

A useful sanity check: after building, select count(*) from fct_orders should equal select count(*) from stg__orders. The verifier checks this.

What the fact looks like

models/marts/fct_orders.sql:

select
    o.order_id,
    o.customer_id,
    c.first_name,
    c.last_name,
    o.order_date,
    o.status,
    coalesce(p.total_amount, 0)  as amount,
    coalesce(p.payment_count, 0) as payment_count
from {{ ref('stg__orders') }} o
left join {{ ref('stg__customers') }}     c using (customer_id)
left join {{ ref('int_order_payments') }} p using (order_id)

Reading it top-to-bottom:

  • {{ ref('stg__orders') }} o is the driving table. Aliased o for readability.
  • left join … customers using (customer_id) — every order has a customer, so inner join would also work, but left join is safer: if a customer record vanishes upstream, you’d rather see the order with nulls than have it disappear from the fact silently.
  • left join … int_order_payments using (order_id) — orders without payments would land here as nulls. coalesce(…, 0) makes the analyst’s life easier: no null dollars in the report.
  • using (customer_id) — DuckDB syntax for “join where columns of the same name are equal.” Equivalent to on o.customer_id = c.customer_id. Slightly cleaner when names line up.
  • No {{ config(...) }} block. The model lives under models/marts/ and inherits +materialized: table from dbt_project.yml — facts almost always materialize as tables (built once, read many times).

Order of joins matters

Putting the driving table first and left join-ing dimensions and aggregates is a discipline. The opposite — starting from int_order_payments and joining out to orders — would leave any order without a payment out of the fact entirely. With the orders table first, those rows survive with null payment values that you can coalesce(…, 0).

The rule of thumb: drive from the table whose grain you want. Everything else is a lookup.

Common pitfalls

  • Grain explosion. Joining stg__payments (the un-aggregated 113-row staging model) instead of int_order_payments blows the row count from 99 to 113. The verifier catches this.
  • Inner join instead of left join. Loses rows silently. If select count(*) from fct_orders is less than select count(*) from stg__orders, you’re filtering rows out somewhere — usually an inner join.
  • Forgetting coalesce. Analyst queries sum(amount) and gets null for the few orders without payments. Better to materialize 0 once than chase the bug downstream.
  • using (id) ambiguity. using only works when the join column has the same name on both sides. Mismatched names need explicit on a.x = b.y.
