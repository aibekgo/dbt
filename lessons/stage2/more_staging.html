Filling out the staging layer

stg__customers is the only staging model so far. The convention is one staging model per source table — 1:1, same grain, just clean enough to be friendly downstream. This exercise adds the missing two: stg__orders and stg__payments.

What a staging model is for

Staging models do light work: rename ambiguous columns, cast types into something normal, alias unhelpful identifiers, and otherwise leave the data alone. They are deliberately boring. The boredom is the point — every downstream model knows it can join to stg__orders without reasoning about whether id means an order id or a user id.

Things staging models do:

  • Rename id → order_id / customer_id / payment_id. Otherwise every join condition is a guessing game.
  • Cast cents to dollars, epoch to timestamp, strings to enums. Anything that’s a “fix the raw shape” rather than “answer a question.”
  • Drop columns nobody uses. Optional, but shrinks the surface area.

Things staging models don’t do:

  • No joins. Staging is grain-preserving — one row in, one row out. If you need to combine tables, that’s an intermediate or mart model.
  • No business logic. No “active customer” rule, no revenue calculations, no de-duplication policies. Those decisions belong upstream of intermediates and downstream of staging.
  • No filtering beyond obviously broken rows (nulls in primary keys, soft-deletes that should be hidden everywhere).

If you find yourself wanting to do any of those, that’s a signal you’re already in int_* or fct_* territory.

What the new files look like

models/staging/stg__orders.sql:

select
    id          as order_id,
    user_id     as customer_id,
    order_date,
    status
from {{ source('jaffle_shop', 'raw_orders') }}

Two renames: id → order_id (so it matches up with payment.order_id downstream) and user_id → customer_id (so it matches stg__customers.customer_id). order_date and status are already well-named.

models/staging/stg__payments.sql:

select
    id                       as payment_id,
    order_id,
    payment_method,
    amount / 100.0           as amount
from {{ source('stripe', 'raw_payments') }}

Two changes worth pointing out:

  • id → payment_id — same reason as stg__orders, disambiguate the id columns at the boundary.
  • amount / 100.0 as amount — Stripe stores money in cents (e.g. 1000 for $10.00). Casting once at the staging layer means every downstream query gets dollars, no surprise multiplications. Use 100.0 (with the decimal) so DuckDB returns a DOUBLE rather than truncated integer division.

The from lines reference the new sources you just declared in multi_source_split — jaffle_shop for orders, stripe for payments. If you forget to update those, dbt errors out at parse time.

Why one model per source table?

Two reasons. First, discoverability — when someone wants to know “what tables are usable downstream?” they look in models/staging/. One file per source table makes that map obvious. Second, isolation of upstream changes — if Stripe drops the payment_method column, you change exactly one file (stg__payments.sql) and every model downstream that joins to stg__payments breaks loudly during testing instead of silently producing nulls.

A common anti-pattern is one giant stg__all_orders.sql that joins customers, orders, and payments. That model is useful, but it isn’t a staging model — it’s a fact (fct_orders), and we’ll build one in the next exercise.

Common pitfalls

  • Same source, wrong source name. source('raw', 'raw_orders') won’t compile after multi_source_split — the source is now called jaffle_shop. Same for stripe.
  • Forgetting the rename on id. A staging model that emits a column called id is fine for dbt, but it makes every downstream join condition (a.id = b.id) ambiguous. Rename at the source.
  • Doing too much. No joins, no filters beyond the obvious, no business logic. If you’re tempted, that work belongs in int_* or fct_*.

Exercise walkthrough

Steps

1. Create dbt_project/models/staging/stg__orders.sql with these contents:

select
    id          as order_id,
    user_id     as customer_id,
    order_date,
    status
from {{ source('jaffle_shop', 'raw_orders') }}

Two renames:

  • id → order_id — disambiguates against the id in raw_payments and raw_customers.
  • user_id → customer_id — matches the column name in stg__customers, so joins downstream read naturally.

2. Create dbt_project/models/staging/stg__payments.sql:

select
    id                       as payment_id,
    order_id,
    payment_method,
    amount / 100.0           as amount
from {{ source('stripe', 'raw_payments') }}
  • id → payment_id — same disambiguation rule.
  • amount / 100.0 — Stripe stores money in cents. Dividing once here means every downstream model already gets dollars. Use 100.0 (decimal) so DuckDB casts to DOUBLE and you don’t get integer truncation.

3. Build everything in the staging folder:

cd dbt_project
dbt run --select staging

You should see three green lines — stg__customers, stg__orders, stg__payments — plus a “Done” summary.

4. Sanity-check the new tables exist with the expected columns:

dbt show --select stg__orders --limit 3
dbt show --select stg__payments --limit 3

You should see order_id and customer_id in the orders preview, and payment_id plus a decimal amount in the payments preview.

5. Press v to verify.

What the verifier checks

  • dbt run --select staging exits 0 — confirms both new files compile and execute.
  • stg__orders and stg__payments exist as objects in dev.duckdb.
  • A small SELECT against each table returns a row, proving the renamed columns landed.

Common failure modes

Symptom Fix
Compilation Error: 'raw' is not a source declared in this project You’re still using source('raw', ...). Update to source('jaffle_shop', ...) or source('stripe', ...).
Binder Error: Referenced column "user_id" not found Misspelled column name. Check data/raw_orders.csv — the column is user_id.
Payment amounts are huge integers (e.g. 1000 for $10) You forgot the / 100.0 cast, or used 100 instead of 100.0 (integer division).
model 'stg__payments' references unknown source 'jaffle_shop.raw_payments' Wrong source. Payments belong to stripe.
